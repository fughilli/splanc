# HITL per-gate performance metrics

Every HITL gate can report the numbers it gates on (latencies, durations, rates) so
they are trended over time per rig and DUT, with the gate's limit drawn next to the
typical value: the [HITL performance](https://splanc.grafana.net/d/hitl-performance)
dashboard. The threshold audit built on this data is
[docs/hitl/gate-thresholds.md](../../../../docs/hitl/gate-thresholds.md).

```text
gate (pi/hitl/harness)  --hitl_metrics.emit()-->  "HITL_METRIC {json}" on stdout
   (or a line it already prints, parsed by legacy_extractors.py)
        |  bazel test --test_output=all  ->  hitl_tests job log
        v
ingest_hitl_metrics.py (fxbench-ingest.yaml, every 3 h; reuses the fx_bench
        |               ingest's API helpers + job-log cache)
        v  assets on the fxbench-data release (only changed ones re-uploaded)
hitl-metrics.jsonl          full history (seeds a fresh CI checkout)
hitl-metrics-summary.json   n/p50/p95/max/limit/headroom/drift per series x lane x rig(/DUT)
hitlm-<series>.json         one per series: points + limit/p50/p95 reference lines
        |  grafanacloud-infinity datasource
        v
dashboards/hitl-performance.json   (generated by gen_dashboard.py)
```

Only `data/ingest_state.json` (run-id ledger + asset digests) is committed.

## Running it

```bash
# incremental, what CI runs (needs a token with contents:write for the release):
python3 ingest_hitl_metrics.py --max-pages 2 --seed-from-release --upload-release
# local, from a log mirror (<run_id>.log.gz + runs.json), no upload:
python3 ingest_hitl_metrics.py --log-dir /path/to/logs --out /tmp/hm --force
# after changing the dashboard layout:
python3 gen_dashboard.py
```

GitHub keeps the HITL job logs for about 30 days, so history starts 2026-10-19.

## Adding a metric to a gate

Prefer emitting from the gate over a legacy regex: the gate knows its limit, and a
format change in a print can't silently drop the series. A gate that emits a
`(gate, metric)` turns off the legacy parse of the same pair automatically.

## Schema v1

Print ONE stdout line per measured value (CI runs `--test_output=all`, so it lands in
the `hitl_tests` job log, which the ingest parses — same mechanism as fx_bench):

```text
HITL_METRIC {"v":1,"gate":"ble_rename","metric":"name_seen_latency","unit":"s","value":1.84,"limit":5.0,"cmp":"<=","ok":true,"phase":"conn","dut":"c6-71226c","rig":"hitl-rig-2","fw":"9d5dbb1...","ts":1763630000.1}
```

Preferred: `import hitl_metrics; hitl_metrics.emit(gate, metric, value, unit, limit=..., cmp="<=", phase=...)`
(it is in the `:harness` py_library; `dut`/`rig` are filled from the active
`hitl_client.Reservation`, `fw` from `$GITHUB_SHA`). If your branch predates the
module, print the line yourself with `json.dumps(rec, separators=(",", ":"))` —
the ingest only needs the `HITL_METRIC` prefix + a JSON object on one line.

If the gate also writes a results JSON, put the same objects in a top-level
`"metrics": [...]` array.

### Fields

| field    | req | type   | meaning                                                                                                                          |
| -------- | --- | ------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `v`      | yes | int    | schema version, `1`                                                                                                              |
| `gate`   | yes | str    | short gate id: the bazel target minus `_netstack` / SKU suffix (`ble_rename`, `improv_fresh_join`, `improv_wrong_password`, ...) |
| `metric` | yes | str    | snake_case quantity name, no unit in it (`name_seen_latency`, `error_at_app_latency`, `notify_latency`)                          |
| `unit`   | yes | str    | one of `s ms us fps cycles bytes count pct kbps`                                                                                 |
| `value`  | yes | number | the measurement (finite)                                                                                                         |
| `limit`  | no  | number | the pass/fail bound the gate applied to THIS value; omit for telemetry-only                                                      |
| `cmp`    | no  | str    | `<=` `<` `>=` `>`: `value cmp limit` = pass (default `<=`)                                                                       |
| `ok`     | no  | bool   | did it meet `limit` (computed by emit())                                                                                         |
| `phase`  | no  | str    | sub-scenario, part of the series key (`idle`/`connected`, `stored`/`absent`, `osc`/`live`)                                       |
| `stat`   | no  | str    | `p50 p95 p99 max mean min` when `value` summarises samples taken inside the gate                                                 |
| `n`      | no  | int    | sample count behind `stat`                                                                                                       |
| `dut`    | no  | str    | DUT unit (`c6-71226c`); default: the Reservation's unit                                                                          |
| `rig`    | no  | str    | rig host (`hitl-rig-2`); default: the Reservation's server host                                                                  |
| `fw`     | no  | str    | firmware commit; default `$GITHUB_SHA`                                                                                           |
| `ts`     | no  | number | epoch seconds of the measurement                                                                                                 |

The ingest adds: `run_id`, `branch`, `sha`, `event`, `time` (run start, ISO), `target`
(bazel label), `attempt` (1-based within the run's log), `src` (`emit` or `legacy`).

Series key on the dashboard = `gate / metric / phase / stat`. Keep names stable:
renaming a metric starts a new series.

### Rules of thumb

- Emit the raw per-trial value (one line per trial), not only a summary, when the
  gate makes several trials — the dashboard computes p50/p95 over all of them.
  Use `stat=` only for values the gate itself summarises over many samples (e.g.
  `live_latency` p50 over 900 controls).
- Emit on FAIL too (value = what was seen when the limit tripped; for a timeout,
  the elapsed time at give-up with `ok:false`). A metric that only appears when it
  passes hides the tail.
- Low cardinality: no IPs, MACs, run ids in `phase`.
- Never let emission fail the gate (emit() swallows errors).

The 20 s / 45 s Improv budgets run from the provisioner's write ack
(`hitl_improv.py` `asyncio.wait_for`), so the precise latency can only be measured
rig-side. A rig-side script may print `HITL_METRIC {...}` to stdout/stderr: the
relayed line lands in the test log and the ingest fills `rig`/`dut` from the
section's `reserved:` line.

`ble_notify_latency` = firmware send (DUT serial timestamp, mapped to host time) ->
central receive callback; emit per notification or `stat=p50/p95/max` + `n` if there
are many. Desk D-75 (occasional ~2 s delay) wants the `max` series.
