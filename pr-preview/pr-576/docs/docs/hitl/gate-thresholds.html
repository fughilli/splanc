HITL gate thresholds: audit (2026-11-20)¶

Every timing and performance limit a HITL gate fails on, compared with what the gate actually measures on the rigs. This answers the owner’s question: where is the acceptance limit far above the typical (p50) value, so loose that a real regression could still pass?

Status: proposal only. No gate is changed by this PR. Each “tighten” recommendation below needs owner approval first (one review-desk item per gate).

Method¶

  • Data. Every hitl.yaml run whose hitl_tests job log is still retained: 2026-10-19 to 2026-11-20, 654 runs on all branches. GitHub keeps HITL logs for about 30 days. The values come from the lines each gate already prints, parsed by pi/hitl/observability/metrics/legacy_extractors.py. That is the same data the HITL performance dashboard plots.

  • Statistics. Each one is over the main lane: pushes to main, the merge queue, and the 6-hourly scheduled runs. PR branches carry work-in-progress failures, so they are left out. n counts samples, and a gate can measure several per run. Limit/p50 and limit/p95 are the headroom; for a floor (>=) the ratio is inverted to p50/limit.

  • Flag. A gate is flagged when its headroom is > 3× p50 or > 2× p95.

  • New fails. For each proposed limit, new fails counts the main-lane samples from the window that passed the current limit but would fail the proposed one. CI’s --flaky_test_attempts=3 retries a failed test. So a per-run rate of x gives roughly x³ at the job level, if retries are independent. They are not independent when the cause is a slow rig.

  • Mesh and BLE rename. These gates are not in CI yet. They run as manual binaries on rig-1 and on the agent/ble-live-rename branch. Their numbers come from the saved run logs under .claude/mesh*/runs and .claude/blerename/runs, so n is small.

  • Rig noise. The main noise sources are:

    • shared 2.4 GHz airtime on the rig APs, with BLE and Wi-Fi coexistence on the C6;

    • the Pi 3/USB2 single bus on rig-3 (fenced out of CI);

    • ssh and tunnel jitter between the GitHub runner and the rig, over the tailnet;

    • queueing while 3 merge-queue runs share 2 rigs.

BLE notify latency (desk D-75)¶

ble_capture_e2e already logs the BLE request→notification round trip per request. The “~2 s” delay shows clearly in the 30 days of CI data:

  • stage requests: p50 324 ms, p95 2.2 s, max 7.8 s.

  • timing requests: p95 1.5 s, max 4.4 s.

  • hello requests: p95 212 ms.

The slow tail is on requests that make the firmware change what it renders (stage, timing, stop), not on hello/start. That points at the firmware’s reply path more than the radio link, but the logs can’t separate the two. It is now a dashboard series: ble_capture_e2e.ble_request_rtt.<kind>, and ble_player_e2e.ble_request_rtt from this PR. The improvflake agent’s planned firmware-send→central-receive metric (ble_notify_latency) will split the delay between the link and the firmware.

Not measured: limits whose value never reaches the log¶

These gates fail on a time that is never printed, so they can’t be audited from CI. Each needs a hitl_metrics.emit() at the listed site; these are follow-ups.

  • osc_deck_follow: OSC applied ≤ 3 s, hitl_osc_deck_follow.py:169.

  • kiosk: revert dt (printed only on failure, hitl_kiosk.py:338); activity push ≤ 5 s (:291).

  • wide_uniforms: 0.5 s apply.

  • fx_debug: resume and advance checks.

  • upgrade_keeps_wifi: lease within 45 s.

  • stable_identity: pong and mDNS latency.

  • no_reboot_no_park: rejoin ≤ 90 s.

  • ota_gate: back-in-app ≤ 120 s (badsig, keyrot).

  • hitl_ws: connect, cert and manifest settle times (90 s each).

  • web_ota_journey: web_seconds (900 s).

  • improv_fresh_join: the dead join_s check (improv_fresh_join_core.py:158). Nothing sets join_s, so the budget check there never fires; the real limit is the provisioner’s timeout.

Reproducing¶

# mirror the retained hitl_tests logs, parse, summarise (no upload):
python3 pi/hitl/observability/metrics/ingest_hitl_metrics.py \
  --log-dir <dir with <run>.log.gz + runs.json> --out /tmp/hm --force
# or straight from the API (what CI runs every 3 h):
python3 pi/hitl/observability/metrics/ingest_hitl_metrics.py --max-pages 20

hitl-metrics-summary.json holds the n / p50 / p95 / max / limit / headroom per series, lane and rig (or rig/DUT) behind this table.
