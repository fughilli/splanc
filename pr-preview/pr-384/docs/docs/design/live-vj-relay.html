Live VJ through the bridge (and the relay)¶

Status: first version implemented. Bridge: agent/src/bridge/live.ts (multiplexer), liveLan.ts (direct LAN endpoint), lanCert.ts (its certificate). Relay: /live in agent/relay/src/index.ts + bridgeObject.ts. App: web/src/net/liveProtocol.ts (the protocol, shared with the bridge), web/src/net/bridgeLive.ts (client), web/src/ui/screens/bridgeLive.ts (the Live via bridge screen, #/bridge). Tests: //agent:relay_live_test, //agent:live_e2e_test, //web:bridgeLive_test.

Problem¶

A Splanc player (ESP32-C6, netstack firmware) serves one TLS/wss session at a time. The app connects to one fixture directly, so a show with five fixtures means five phones, or hopping between them. The bridge (splanc-agent bridge, usually the Pi appliance) already holds one session to every player on its LAN for cloud agents. Live VJ reuses it: the app connects to the bridge once and drives every fixture from there — from anywhere through the cloud relay, or directly on the LAN when it can reach the bridge.

Shape¶

 app (PWA / iOS) ──wss /live──▶ relay Worker ─▶ BridgeObject ──(bridge's outbound ws)──┐
        │                         (pass-through, hibernatable)                          ▼
        └───────────wss://<bridge LAN IP>:8443/live (direct, preferred) ──────▶ bridge: LiveMux
                                                                                │ one /ws per player
                                                                                ▼ (shared with MCP agents)
                                                                         players on the LAN

The same live protocol runs on both paths. The relay never parses it: it authenticates the socket, then passes each text message through verbatim, tagged with a connection id, inside the bridge socket it already has.

  • Why a WebSocket through the BridgeObject rather than tunnelled HTTP like /mcp: a slider is many tiny one-way messages. Over HTTP each would be a Worker request and a DO request (100 k/day each); over a hibernatable WebSocket an incoming message costs 1/20 of a DO request, outgoing ones are free, and the upgrade is the only Worker request.

  • Credential in the subprotocol list (["splanc-live.v1", "bearer.<token>"]): browsers can’t set headers on a WebSocket, and a query-string token ends up in logs. The server answers with Sec-WebSocket-Protocol: splanc-live.v1 only.

  • Direct path and the PWA’s constraints. The app is served over https (splanc.io/app), so it may only open wss:// (mixed content blocks ws://). The bridge therefore serves TLS with its own certificate, exactly like a player does, and the same trust-on-first-use step applies: a browser needs the user to open https://<ip>:8443/ once and accept the certificate (the screen links it, and shows the SHA-256 the bridge vouched for over the relay so it can be compared). The native (iOS) wrapper can instead pin that SHA-256 — it comes over the authenticated relay channel before the LAN is ever dialed — which is strictly better than TOFU. Chrome’s Local Network Access permission (public origin → private IP) applies here as it already does for the app’s direct player connections.

  • Path selection. With a stored LAN ticket the client tries direct first (3 s timeout), else the relay; after a relay welcome it tries direct in the background and switches (closing the relay socket, so a direct session costs the relay nothing). A browser can’t tell “untrusted certificate” from “not on that network”, so the screen says both.

Protocol¶

A small JSON envelope (web/src/net/liveProtocol.ts), not raw ledmapper.proto ClientMessage frames addressed to a player:

  • the bridge owns the device sessions and their single-flight reply waiters (LedMapperClient); forwarding raw frames and replies from another client would race them (a fire-and-forget set_crossfade’s welcome echo can satisfy someone else’s pending set_brightness);

  • fan-out (to: ids, names, rooms, "all"), coalescing and arbitration are bridge-level ideas with no protobuf arm;

  • uniforms go by name and are resolved per player against that player’s own manifest (slots can differ across firmware versions);

  • an allow-list by construction: there is no way to express re-flash, re-map or wiring (FORBIDDEN_TYPES stays enforced at the bridge’s wire guard too);

  • the relay bills per message, not per byte, so JSON costs nothing extra.

No ledmapper.proto change, so no field-number collisions with other branches.

Coalescing and rate limits¶

  • App: one c frame per tick at most, leading edge (the first move after a quiet tick goes at once), carrying every control that changed (all sliders, crossfade, brightness), last value wins. A slider’s release flushes immediately with commit: true (uncommitted while dragging: no flash wear on firmware with uniform_commit). Measured in //web:bridgeLive_test: 50 moves in one tick → 1 frame.

  • Relay: > 60 messages/s on one socket are dropped (with one notice per second): a runaway client can’t burn the account’s daily budget. ≤ 8 live sockets per bridge; messages ≤ 256 KiB (an effect’s source).

  • Bridge: per player, pending controls merge; a flush loop sends at most one frame per kind per 16 ms, through the player’s serialized session queue (so they interleave safely with agents’ tool calls). Uniforms are truly fire-and-forget (set_uniforms has no reply); crossfade, brightness and keypoint blends await their echo (see Protocol), which coalesces them naturally to one per device round trip.

Free-tier cost (Workers Free, checked 2026-10)¶

DO incoming WebSocket messages bill at 20:1 as requests (100 k/day); outgoing and auto-responses are free; duration is billed while the object is awake (128 MB × wall time, 13,000 GB-s/day); a hibernated object with open sockets costs nothing.

Auth¶

Pairing is exactly the agent flow: the user reads the code off the bridge’s screen and the app redeems it at POST /pair (Accept: application/json, label = the device name the user typed) for a personal token spl_pt_… — revocable, hashed at the relay, and the same credential works for /mcp. Per-client: every install has its own token (its own grant). The relay checks it on the upgrade (a malformed one is refused by the Worker without waking a Durable Object) and tells the bridge the grant id with live_open.

The LAN ticket (spl_lt_<43>) is minted by the bridge for the relay-authenticated client, stored as SHA-256 in <state dir>/live-clients.json (mode 0600), one per client_id, 30-day expiry, re-minted on every relay hello. Revocation:

  • Forget this bridge in the app → POST /revoke → the relay closes that grant’s live sockets (4003) and sends the bridge {"t":"revoked","grants":[…]} → the bridge closes its LAN sessions of that grant and deletes their tickets;

  • the bridge’s revoke-all (display button / bridge-ctl revoke-all) → every live session ends, every ticket is deleted, even if the relay is unreachable;

  • residual: the relay tells the bridge about a revocation only while the bridge is connected; a credential revoked while the bridge is offline from the relay keeps its LAN ticket until the ticket expires (30 days) or a revoke-all. Acceptable on a LAN whose players have no auth of their own; a follow-up can have the bridge re-validate tickets’ grants with the relay on reconnect.

Arbitration (multiple apps + MCP agents on one bridge)¶

  • The bridge is the only client of each player; every writer (live apps, MCP sessions) goes through the player’s serialized DeviceSession queue, so device traffic never interleaves mid-request.

  • Default: last writer wins per control.

  • Show Mode lock (q lock {on}, the screen’s switch): the holder’s commands pass; every other writer is refused with the holder’s name — other live apps get err locked, MCP tools get a ToolError (”… is being performed live (Show Mode lock held by “Kevin’s iPhone”) …”) from DeviceSession.assertUnlocked, which every mutating method calls — including crossfade_to’s cue and fade and rollback_effect. Reads (list, list_decks, effect, perf, preview) still work. A lock outlives its holder’s disconnect by 30 s (a phone switching from Wi-Fi to cellular reclaims it with its client_id), then releases.

  • Framerate autoscaler (FUG-82). The bridge never flushes controls to a player faster than it renders (gap = max(16 ms, 1000 / its current fps)), each player in the list carries fps {current, target, auto, lagging, achieved} (changes ride the 2 s players push), and a change of fps_state{lagging} — the effect can’t hold the floor or a pinned rate and runs at the rate it achieves; the player never parks it — is pushed to every app at once as {"t":"fps", lagging, achieved_fps, …}; the screen mentions it (advisory, not an error) and marks the fixture as lagging.

  • One deck model. The live mux and the agent tools share DeviceSession’s deck state (which deck is live, the crossfade position, the effect on each deck and the parked rollback target). A performer’s Cue A/B is cueDeck (upload + activate on that deck without touching the crossfade; cueing the idle deck parks the live effect as the rollback target, as crossfade_to’s cue does) and the crossfader is liveCrossfade (the side it rests on is the live deck; landing on the parked deck swaps, like a crossfade_to that ends there). So after a performer cues B and fades to it, list_decks says B is live and rollback_effect fades back to A — tested in //agent:live_e2e_test.

Multi-fixture sync¶

  • A deploy to more than one player runs Hub.alignTime afterwards (one shared effect-clock epoch via set_time_base; the reply carries skew_bound_ms), and Sync clocks does it on demand. Effects are time-driven, so aligned fixtures stay in phase.

  • One c frame fans out to every selected player in the same event-loop turn; skew between fixtures is the difference of their bridge → player hops (LAN, a few ms), not the app → bridge path.

When things drop¶

Event

What happens

A fixture drops

Its chip greys out (players push within 2 s); controls for it get err offline (rate-limited) and are dropped, not queued; the session reconnects with backoff, and the mux re-dials a player down > 20 s. Effect state is the device’s (re-cue if it rebooted blank).

The bridge loses the relay

The relay keeps the app’s socket and tells it bridge offline; app messages meanwhile get the same notice. When the bridge reconnects it sends caps, the relay re-opens every live session, says online, and the app says hello again. Locks wait out the 30 s grace.

The bridge restarts

Same, plus in-memory locks are gone; LAN tickets persist.

The app loses its network

Reconnects with backoff (0.5 → 15 s), direct first if it has a ticket.

Relay over its daily limit

/live upgrades fail until 00:00 UTC; the direct path still works.

UI¶

⋯ → Live via bridge (#/bridge). Unpaired: pairing code + device name (+ relay URL under Advanced). Paired: a status pill “Live direct (LAN) · 12 ms” / “Live via relay · 95 ms” / “Bridge offline” (tap = latency probe: app ⇄ bridge and bridge ⇄ each fixture); when on the relay with a LAN endpoint advertised, a line offering “trust the bridge once” + Go direct with the certificate fingerprint; fixture chips (All, rooms, each fixture; grey = not connected, 🔒 = locked); brightness; effect picker with Cue A / Cue B; crossfader + HSV switch; “sliders edit deck B”; Show Mode lock; Sync clocks / Identify / Latency; the uniforms shared by every selected fixture’s active effect (sliders, toggles, colours) and its keypoint pads; Forget this bridge.

The existing direct-to-device screens (Show Mode, the editor) are unchanged; when a fixture is held by the bridge, the app’s own direct connection to it can’t get a session — use the bridge screen.

Relay changes (backward compatible)¶

  • GET /live (+ forwarded by web/_worker.js RELAY_PATHS on splanc.pages.dev).

  • BridgeObject: app sockets tagged app / app:<id> with attachment {app, fam, label}; new frames live_open, live, live_close, revoked (relay → bridge) and caps, live, live_close (bridge → relay). An older bridge never sends caps, so /live answers 501 bridge_outdated and nothing else changes for it; an older relay never sends live frames to a newer bridge. No storage schema change, no DO migration.
