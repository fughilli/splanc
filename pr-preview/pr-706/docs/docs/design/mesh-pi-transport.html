Mesh on a Raspberry Pi: the radio transport¶

Status: research + prototype (PR #533 on agent/mesh-m1). Companion to mesh.md: §3.2 (the Backhaul seam), §4 (the 802.11 backhaul: framing, channels, BLE coex), §5 (envelope, MTU), §10 and §15 (M10, the IP backhaul). The Pi as a high-capacity custodian (RAM, storage) is modelled separately; this document covers how a Pi gets Splanc mesh frames on and off the air.

1. Summary¶

Question. How does a Pi (the bridge pi/bridge, the Pi player pi/player_rs, a HITL rig) send and receive the mesh’s 802.11 frames on the same channel as the C6s, ideally while it stays associated to Wi-Fi, and with what latency, airtime and reliability?

Owner decisions (2026-11-17), after the first round: Pis mesh without extra hardware, on their own Broadcom radio through the firmware passthrough; the USB C6 coprocessor and USB adapters are secondary. The mesh frame becomes Public Action (category 4, action 9) (mesh.md §4.1, §3 here). Wi-Fi power save is off on mesh Pis. “No RSSI, no ACK status” was not accepted without digging below the driver; this round did that.

Answer, measured on two Pi 3B+ (CYW43455, stock firmware 7.45.265, kernel 6.12.87):

  1. TX: the firmware’s actframe iovar, reached through brcmfmac’s vendor DCMD command. The normal nl80211 path is closed: cfg80211 refuses category 127 from a station (ENOTCONN), and brcmfmac’s mgmt_tx drops every action frame that is not P2P or GAS, category 4/9 included (“Unknown Frame”, measured). The passthrough sends our exact frame on any channel, associated or as an AP.

  2. RSSI and ACK status: kprobes on the driver’s own event handlers, from userspace. On SDIO the firmware’s events never reach a socket (the driver consumes them), and the driver drops the RSSI it is given. But the values are in the handlers’ arguments, and tracefs kprobes read them with no kernel patch: RSSI per frame (−18 dBm median between the two Pis), the firmware’s µs receive time, and ACK / no-ACK for every unicast. Measured: 300/300 unicasts to the peer ACKed, 100/100 to an absent MAC reported NO_ACK.

  3. Delivery and latency (both Pis associated to the rig AP on ch 1): broadcast 93.5 % per hop (281/300, 279/300); unicast 100 % of 300 exchanges; ping/pong RTT p50 15 ms, p90 36 ms; actframe → on-air completion p50 4.8 ms (broadcast), 7.5 ms (unicast incl. ACK), 37 ms when the peer is absent (the firmware’s retries).

  4. Per-send host cost: 0.3–0.5 ms of CPU. Wall time is 1.1–1.5 ms when the SDIO bus is busy and ~4.4 ms when it has clocked down (the driver idles the bus after ~10 ms, hard-coded); sending only the used bytes of the iovar saves ~0.3 ms. A TX thread hides the wall time.

  5. AP mode works for RX and TX: a Pi hosting the AP on the mesh channel (the bridge at a site without Wi-Fi) received 182/200 broadcasts with RSSI and got 100/100 unicasts ACKed. Its frames were not passed up by a Pi associated to a different AP (§4.3).

  6. Pi ↔ C6, over the air: a rig C6 running a vendor-stack probe received 394/400 frames from a Pi (and parsed them as Splanc frames: the reference bytes hold); a Pi received 317/351 of the C6’s. The Pi’s firmware sends action frames at 1 Mb/s DSSS.

  7. IP backhaul (M10): the same frames in UDP multicast, 200/200, RTT p50 1.86 ms between the Pis over Ethernet.

Recommendation. The Pi’s own radio, through actframe + the kprobe tap, is the primary Pi transport: it delivers what the C6s do (frames, RSSI, ACK status) at a few ms of latency, with no hardware and no kernel change. Add the IP backhaul wherever Pis share a LAN. Keep the USB C6 coprocessor (the owner has C6s) for a Pi whose own radio must stay on another channel. Buy one AR9271 adapter only for a sniffer/debug role (§2.2).

2. Options¶

2.1 The Pi’s own radio (brcmfmac): primary¶

All Pis with Wi-Fi use a Broadcom/Cypress (now Infineon) FullMAC chip behind brcmfmac: BCM43438/CYW43438 (Pi 3B, Zero W), CYW43436 (Zero 2 W), CYW43455 (Pi 3B+, 4, 5, CM4). The firmware runs the 802.11 MAC; Linux sees an Ethernet-like device plus control iovars.

TX through nl80211 (NL80211_CMD_FRAME): closed.

  • cfg80211 (every driver). cfg80211_mlme_mgmt_tx (net/wireless/mlme.c) checks every action frame whose category is not Public (4): a station may only address its own AP (-ENOTCONN). Measured on the Pi: ENOTCONN for every category-127 frame. Public Action passes this check.

  • brcmfmac (brcmf_cfg80211_mgmt_tx → brcmf_p2p_send_action_frame, p2p.c). It classifies the body: P2P public action (4/9 with the WFA OUI and type 9), GAS, or P2P action (127 with the WFA OUI). Anything else logs “Unknown Frame” and reports no-ACK without sending. Same code upstream and in rpi-6.12.y. Measured: our 4/9 frame passes cfg80211 and is dropped here (Unknown Frame: category 0x4, action 0x9). The Pis’ logs show wpa_supplicant’s own radio-measurement and WNM frames dropped the same way.

TX through the firmware’s actframe iovar: works. brcmfmac registers one vendor command, BROADCOM_OUI/BRCMF_VNDR_CMDS_DCMD (vendor.c), which passes a buffer to brcmf_fil_cmd_data_set/get: any firmware ioctl or iovar, from userspace, with CAP_NET_ADMIN. actframe takes brcmf_fil_af_params_le (channel, dwell, BSSID, then DA, length, packet id, up to 1800 bytes of body). The firmware builds the header (A1 = DA, A2 = own MAC, A3 = the BSSID passed), picks the rate and transmits, off-channel if asked. Two handler details: brcmf_cfg80211_vndr_cmds_dcmd_handler uses the header’s len as the set length, so it must cover the iovar buffer; the body need not be padded to 1800 bytes (measured).

RSSI, receive time and ACK status: the kprobe tap (ktap.rs). What the firmware gives and where it goes:

Where the events could reach userspace:

  • A packet socket on ethertype 0x886c: brcmfmac does pass event frames up the netdev for the bcdc data path (brcmf_rx_frame → brcmf_netif_rx), but on SDIO this firmware sends events on the bus’s event channel, which goes to brcmf_rx_event and is freed. Measured: no event frames on wlan0.

  • nl80211 vendor events: brcmfmac defines none.

  • Firmware counters/iovars (counters, pktcnt, rssi, sta_info): aggregate or per-AP only, a 0.8 ms ioctl each; not per frame.

  • tracefs kprobes on the two handlers (used). The values are in the handlers’ arguments. Two kprobe_events lines (in ktap.rs) fetch rssi, mactime, chanspec, the sender (e->addr), the body (as x32[64], 256 bytes: the 6-byte prefix plus a 250-byte mesh frame) and e->status, in a private tracefs instance with the mono clock. Needs root, CONFIG_KPROBE_EVENTS (on in the NixOS and Raspberry Pi OS kernels) and the brcmfmac symbols (present: both handlers are in kallsyms). It is removed on exit. The tap is matched to the nl80211 copy of each frame by sender and body; when nl80211 registration is impossible (AP mode, §4.3) the tap’s body is the RX path.

The kernel fix (sent upstream; carried in our Pi images). A four-patch series for brcmfmac on wireless-next makes the plain nl80211 path work: (1) pass rxframe->rssi to cfg80211; (2) complete action frames sent without a dwell time on ACTION_FRAME_COMPLETE (the firmware sends no OFF_CHAN_COMPLETE for them, so each waited the 2 s P2P_AF_MAX_WAIT_TIME); (3) count NO_ACK on a group-addressed frame as sent instead of retrying it; (4) send other action frames with the caller’s dwell time instead of “Unknown Frame” (the P2P default of 200 ms makes the firmware answer BCME_BUSY to the next frame). Tested on the DUT Pis with brcmfmac rebuilt for their 6.12.87 kernel: NL80211_CMD_FRAME unicast 100/100 ACKed, absent peer 20/20 NO_ACK, broadcast 100/100 reported sent (94/100 distinct received), NL80211_CMD_REGISTER_FRAME 92/100 received with NL80211_ATTR_RX_SIGNAL_DBM. Two limits remain: ~50 ms per send (the driver’s 40 ms P2P_AF_RETRY_DELAY_TIME sleep before the first attempt, left alone), and the 6.12 trees lack upstream’s mgmt_tx channel fix (f2d7c3c380bf): without it, NL80211_CMD_FRAME without a frequency sends with a bogus channel and the firmware answers BCME_BUSY. The passthrough is faster (~1–5 ms per send).

Carried in the Pi images (owner’s decision). The player image (pi/provisioning/nix/brcmfmac-actframe.nix) carries the four patches plus a backport of the f2d7c3c380bf channel hunk (brcmfmac-actframe/0005-*.patch). Only the driver is rebuilt, from the image kernel’s own source, config and patches; the modules go to lib/modules/<ver>/updates, which depmod prefers over the kernel’s. The kernel’s dev output is in no binary cache we pull from (the kernel itself is, on fugstudio.cachix.org), so the build reads the MODVERSIONS CRCs of every imported symbol from the stock modules and fails unless nothing is undefined and every export the stock modules import keeps its stock CRC (the rebuilt driver is ABI-identical to the stock one). The image writes the patched module’s source version to /etc/splanc/brcmfmac-actframe.srcversion; pimesh --via auto (the default, radio::auto_via) uses Nl80211Mgmt when /sys/module/brcmfmac/srcversion matches it, and falls back to BrcmActframe + the kprobe tap on any other kernel or module. --via brcm|nl80211 still forces either.

Per-send cost (measured, §4.2): 0.3–0.5 ms CPU per actframe. Wall time is dominated by the SDIO control round trip: ~1.1–1.5 ms when the bus is awake, ~4.4 ms when it has clocked down. sdio.c sets bus->idletime = BRCMF_IDLE_INTERVAL (one ~10 ms watchdog tick) with no module parameter, so at a 50 ms send interval every send pays the wake-up. Mitigations: send from a dedicated thread (the mesh loop never waits), send unpadded iovars (−0.3 ms), and let traffic keep the bus awake. One actframe is in flight at a time: back to back, the firmware answers EBADE (busy), which the backhaul reports as back-pressure; ~320 frames/s accepted.

Retry limit and rate. brcmf_fil_af_params_le has no rate or retry field; the firmware picks the rate and uses its management-frame retry policy. Measured: a unicast to an absent peer completes with NO_ACK after a median 37 ms (p99 98 ms), consistent with the short retry limit of 7 reported by iw at a low basic rate. Not changed in this round.

Gotchas found on the bench:

  • Power save must be off. With PS on, the receiver caught 3 of 40 broadcasts (it sleeps between AP beacons; nobody buffers mesh frames for it). Now in both Pi images (pi/bridge/image/nix/bridge.nix already had it; pi/provisioning/nix/mesh.nix adds it to the player).

  • Pass the channel explicitly. actframe with channel 0 delivered 1–18 %; the backhaul resolves 0 to the interface’s channel.

  • One registration per prefix per interface. A second process registering the same match gets EALREADY; the backhaul then uses the tap’s bodies.

nexmon (patched firmware for monitor mode and injection): not needed. Stock firmware already sends and receives our frames, and the tap gives RSSI and timestamps. nexmon’s patched binaries cannot be redistributed (Cypress’s licence covers the unmodified file), are tied to one firmware build and kernel, and injection on the 43455C0 has broken across firmware updates.

Which to buy, and why. The Pi’s own radio now covers the transport, so an adapter earns its place only where it adds something:

  • One AR9271 adapter (ath9k_htc; Alfa AWUS036NHA, or TP-Link TL-WN722N v1): a mesh sniffer and reference receiver for HITL. It gives hardware TSF timestamps and RSSI for every frame on the channel (radiotap), honours injected retry counts, is 2.4 GHz-only (the mesh’s band), draws little USB current, and its firmware is open. Use: debugging, per-frame airtime and retry analysis, and a time-sync reference for M4.

  • A second radio for a Pi that must stay on a 5 GHz venue AP while meshing on 2.4 GHz. actframe can send off-channel, but the Pi hears the mesh only during the dwell after each send. A USB C6 does this job equally well and the owner has C6s, so no adapter is needed for it.

Not recommended: MT7921AU (power-hungry on Pi USB budgets, no gain for 2.4 GHz), rtl8xxxu and rtw88 USB (weak injection).

2.3 A USB-attached ESP32-C6 as the radio coprocessor: secondary¶

The C6 runs the netstack and M3’s 802.11 backhaul and passes whole Splanc frames to the Pi over USB-Serial/JTAG (SLIP, serial.rs): TX, CHANNEL, RX (rssi, C6 timestamp, frame), TX_DONE (acked / not), HELLO (MAC). The host side and its tests are in this PR; the C6 bridge task follows M3. Use it for a Pi whose own radio must stay on another channel or band. It is also the reference implementation of the mesh radio.

2.4 BLE¶

BLE is the app’s way into a gateway (GATT; mesh.md §4.3, §10.2) and Improv provisioning; not a mesh backhaul (a C6 would have to scan, taking radio time from Wi-Fi). A Pi can be a BLE gateway with BlueZ; nothing here depends on it.

2.5 The IP backhaul (M10)¶

The same Splanc 802.11 frames in UDP (udp.rs): multicast 239.83.77.1:47811 for broadcast, the learned peer address for unicast, MTU 1400. Needs UDP 47811 open in the NixOS firewall (closed today) and LAN multicast (use udp::Fanout::Peers across routed networks).

Action code 9 is the standard vendor-specific Public Action; the Wi-Fi Alliance’s uses of 4/9 (P2P, DPP, NAN) are keyed by its OUI 50:6F:9A, so a CID cannot collide. So category 4 buys mac80211 adapters full managed-mode TX and RX; it does not change brcmfmac, where the passthrough stays (or the kernel patch of §2.1).

Changes made: frame.rs defaults to Category::PublicVendor, the reference vector is now d0 00 … 04 09 0a 5c 4d 01 … (golden_public_vendor_frame), category 127 still parses; mesh.md §4.1 updated on agent/mesh-design. M1 (#520) needs no change: its link module encodes the LinkFrame only and leaves the 802.11 framing to M3.

4.3 What it means¶

  • Delivery. ~94 % per broadcast hop, 100 % for unicast with the firmware’s retries; the tap now tells the backhaul which unicasts failed. Against M3a’s ≥ 95 % one-hop target, broadcast is just under; the flood’s redundancy and want-ack cover it.

  • Latency. One hop is ~7 ms each way; most of it is the SDIO control path, not air time. Fine for control; apply_at hides it.

  • Time. The tap gives the firmware’s µs receive time (mactime) per frame: a usable hardware RX timestamp for M4’s time sync (its relation to the Pi’s clock is still to be calibrated, e.g. against the beacon TSF).

  • AP-hosting. A Pi hosting the AP sits on the mesh channel for good, which solves the “Pi unassociated” gap: it receives everything and its unicasts are ACKed. The station Pi not passing the AP’s frames up looks like the firmware filtering frames whose A3 is another BSS’s BSSID: in AP mode the firmware stamps its own BSSID into A3 (confirmed by the C6, §4.4). Every C6 member matches on the action body (mesh.md §4.1), so it is unaffected; only a Pi member associated to a different AP misses an AP-hosting Pi’s frames.

  • Rate. The Pi’s firmware sends action frames at 1 Mb/s: a 250-byte mesh frame is ~2.3 ms of air. Fine at mesh.md §10.3’s rates; the firmware’s actframe has no rate field, so a faster rate would need the firmware’s management-rate iovars (not tried).

6. Hardware test plan (remaining)¶

  1. Pi ↔ C6 with M3’s netstack backhaul once it exists (the reference bytes are the contract); today’s oracle is the vendor-stack probe.

  2. Pi 4/5 and Zero 2 W: repeat §4.2 (the 43455 firmware on Pi 5, the 43436 on Zero 2 W).

  3. Soak: 1 h of pimesh node traffic at mesh.md §10.3’s rates; AP links and C6 DUT health.

  4. AR9271 (to buy): sniffer/reference receiver; airtime and retry analysis.

  5. mac80211_hwsim in a NixOS VM test (CI): the nl80211 managed path with Public Action.

  6. Management-frame rate: try the firmware’s rate iovars to send action frames at 6 Mb/s OFDM (a sixth of the airtime).

7. Running the mesh stack on Linux¶

The mesh crates are no_std and build unchanged for the host. A Pi node is splanc_mesh::Node<WifiBackhaul<R>, P> with R = Nl80211Mgmt on the image’s patched brcmfmac, else BrcmActframe (radio::auto_via), driven every ≤ 5 ms; sends should move to a TX thread so the loop never waits on SDIO (or, on the patched driver, its ~50 ms per send). Needs root (or CAP_NET_ADMIN for the registration and the vendor command, plus tracefs access for the tap on a stock kernel). The patched driver comes with the image (§2.1).

7.1 The Pi bridge as a member (issue #697)¶

pimesh serve (pi/mesh_radio/src/bridge.rs) is that node for the bridge: the full MeshStack with Class::Pi, over WifiBackhaul<ThreadedRadio> (the radio on its own thread, so a 1-5 ms passthrough send or the patched driver’s ~40 ms sleep never stalls the loop), a P-256 device key in /var/lib/splanc-mesh/device.key and the mesh state beside it (written atomically). The bridge image runs it as splanc-mesh.service (pi/bridge/image/nix/mesh.nix, user splanc-mesh with CAP_NET_ADMIN only), from the agent bundle pinned in the image (pi-bridge/mesh/pimesh, a static aarch64 musl build).

  • Membership. The agent provisions it with the mesh id and the admin’s public key only, so it joins by approval: a gateway lists it as pending and the admin admits it in the app. With an admin key it re-provisions or leaves only with the provisioner token it issued (D-324). It never holds the admin secret, signs nothing and starts no epoch.

  • Kind. Its status and join carry firmware = FNV-1a(“splanc-bridge”) (0x18d4bfec; fixtures send the FNV-1a of their version), fps 0 and the Pi’s free memory. Every gateway passes the value through unchanged, so the app draws it as a bridge on the mesh map with no firmware change.

  • Links. WifiBackhaul::links reports each neighbour’s running RSSI and its unicast delivery from the radio’s per-destination TX status (nl80211 cookies on the patched driver, ACTION_FRAME_COMPLETE on the passthrough); no ranges (the Pi has no fine timestamps).

  • Control. Relayed control on the allow-list is answered OK (nothing to apply); anything else is refused, as on a C6. Scene blobs are fetched into RAM (16 at most), so it can serve them.

  • Channel. AP-anchored, like the C6s: it stays associated to its Wi-Fi and announces that channel. When the mesh’s adverts say another one, its status says so and the screens ask the user to move the bridge to the lamps’ 2.4 GHz network; it never hops off its own AP.

  • Agent (agent/src/bridge/mesh.ts): reads it over /run/splanc-mesh/mesh.sock, carries the app’s join/leave (live mesh query), and relays mesh traffic for its tools through a meshed fixture on the LAN (get_mesh, mesh_send). On a mesh with an admin key it unlocks that gateway only as a delegate: the app certifies the bridge’s own delegate key, and members enforce the delegate rules (admin.rs).

8. Decisions for the owner¶

  1. Kernel patch: decided (carry it in our Pi kernels now; the tap and passthrough stay as the fallback for stock kernels, §2.1). Open: the ~50 ms per send on the plain path. A local sixth patch could skip the 40 ms P2P_AF_RETRY_DELAY_TIME before the first attempt for non-P2P action frames (not tested on hardware).

  2. Buy one AR9271 adapter (~$15–35) for a HITL mesh sniffer. Nothing else is needed.

  3. Open UDP 47811 in the Pi images when the IP backhaul ships (M10).
