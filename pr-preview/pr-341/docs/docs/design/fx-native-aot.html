Native (AOT) effect execution on the ESP32-C6¶

Status: design + stages 1–2, rebased onto main (#350 fused ops, #328 memo), plus the signature-checking infrastructure (this PR). The trust model is decided (2026-10-28, “Trust” below): unsigned on-device lowering, and user-key HMAC signatures for prebuilt images, with a public dev key on every device for now. Stage 3 (wiring both into player_app) remains. Background numbers: fx-perf-study.md, “Q1 — the native ceiling” and “A native AOT path: feasibility”.

Why¶

Through the VM, a typical effect costs 5–35 k cycles per LED on the C6. That’s 2–5× more than native code doing the same float maths, and 7–70× more than a fixed-point native version (study, Q1). Most of the gap is interpretation: ~54 cycles of dispatch per opcode, operand-stack traffic, and a fixed ~1,790 cycles per VM invocation. At 2048 LEDs, only a solid fill fits a 33 ms frame through the VM. Native code is the only route to 2048 LEDs at 30 fps for non-trivial effects.

What gets lowered¶

Input: verified .fxb bytecode, not source. The AOT lowering (firmware/fx_aot, a no_std + alloc crate) takes exactly the bytes the device already accepts and executes. The VM stays the semantic reference. The native code is a translation of that bytecode, and the differential tests check it against the VM.

Load-time verification inside the lowering. It refuses (and the VM keeps the effect) unless all of these hold:

  • every opcode decodes, and every branch, jump and call target is an instruction boundary inside the code;

  • the operand-stack depth at every instruction is the same along every path (abstract interpretation over the CFG). For a user function, depth is measured relative to the function’s entry;

  • depth never goes below 0 or above MAX_STACK; every local, state and uniform slot operand is in range;

  • no opcode outside the supported set appears. JitCall and the I2C intrinsics are always refused; drivers (FLAG_DRIVER) stay on the VM.

Fused superinstructions and the memo cache (main, #350/#328). Before lowering, fx_aot::defuse expands BinTop, BinPair, PushConsts, LoadCtxLanes and MulAdd into the base opcodes they fuse (each fusion is exact in fx_vm), and turns the per-LED memo brackets LoadLedCache/StoreLedCache into no-ops. Native code binds no memo cache, which the VM defines as running the original code. Branches are re-targeted. Each expansion carries a budget weight (1 on its first op, 0 on the rest), so the native per-block budget decrement still counts a fused op once, as the VM does. The generic helper reads operand bytes from the expanded stream, so an image ships them as Image::op_code (and a .fxn carries them). The memo pass’s per-frame prepare entry (Program::prep_entry) is lowered as a third entry (Image::prep_off); the host runs it once per frame after update(), where the VM runs it lazily before the first LED. A fixed-point frac operand above 30, which the VM now faults on, keeps the effect on the VM.

Because depth is static, every operand-stack slot has a fixed home at compile time, and no runtime stack pointer is needed:

  • slots 0..7 live in callee-saved registers s2..s9, so they survive helper calls without spills;

  • deeper slots live in a frame next to the locals, at fixed offsets from one base register.

Opcode lowering:

  • Inline: const pushes (lui/addi), local/state/uniform loads and stores at static offsets, every integer and fixed-point op, compares, branches and jumps, Swizzle/Swap/Pop (register moves), LoadCtxFix, the superinstructions, Ret/RetRgb8/RetRgbFix.

    • MulFix is mul + mulh + shift-combine.

    • DivI/ModI inline the VM’s divide-by-zero → 0 rule. RISC-V’s INT_MIN / -1 already matches Rust’s wrapping_div.

  • Helper calls: soft-float arithmetic and compares, the maths opcodes, colour, hash, palette, the vector float ops, i64 fixed divides, indexed (dynamic) array access, buffers and textures, graph queries. A helper is a plain extern "C" Rust function. It calls the same fx_vm function the interpreter’s arm calls, or repeats the arm’s expression exactly, so results are bit-identical by construction. On the host, the emulator dispatches the helper table to the same Rust functions.

Expected speed. The study’s f32 twins call the same helpers and measure 2–5× over the VM. This lowering is simpler than hand-written Rust: no register allocation of locals, and one helper call per float op. It should land between the JIT and the f32 twins on float effects. On integer/fixed effects, where almost everything is inline, it should land close to the q16 twins. Stage 2 measures it on a real C6.

Sandbox (applies to every native image, signed or not)¶

The lowering emits a deliberately narrow instruction grammar. A separate instruction-stream verifier (fx_aot::verify, run on the device after lowering or after signature checks) re-checks it independently. It decides from three inputs only: the words, the declared entry offsets, and a VerifyLimits { frame_bytes, state_bytes, budget }. The lowerer/arena that allocates the buffers supplies the limits; nothing is inferred from the image. Image::verify() uses VerifyLimits::DEFAULT: a FRAME_WORDS frame, MAX_STATE state words, and the VM’s default budget. A rejected image stays on the VM.

Verifier rules¶

An image is a sequence of fixed sequences and body words. The fixed sequences are byte-exact copies of prologue_words(budget), epilogue_words() and exit_stub_words() in verify.rs. The lowerer emits those same functions, so the two can’t drift.

  • R1 Entries and fallthrough. Each declared entry holds the exact prologue: addi sp,sp,-64, save ra,s0..s11 to 0..48(sp), then s0=a0, s1=a1, s11=a2, and li s10, budget. Each entry is word 0 or follows an unconditional transfer (ret / jal x0). A prologue anywhere else is rejected. The image’s last word must be unconditional, so nothing falls off the end. The caller calls only declared entries, with a0 = its NativeCtx, a1 = a frame_bytes frame, and a2 = a state_bytes state array.

  • R2 Reserved registers. A body instruction may write only x0, t0..t6, a0..a7 and s2..s9. ra, sp, gp, tp, s0, s1, s10 and s11 are written only by the fixed sequences. There are two exceptions: the helper call (jalr ra, 0(t0)) writes ra, and the canonical budget decrement (R7) writes s10. This also covers loads: a lw into any of those registers is rejected outside the epilogue.

  • R3 Return. ret (jalr x0, 0(ra)) is legal only as the last word of an exact epilogue. The epilogue reloads ra,s0..s11 from the prologue’s save slots, then runs addi sp,sp,64 and ret. The body can’t address sp (R4), sp is never written outside the fixed sequences, and no branch may enter an epilogue past its first word (R6). So every ret returns to the caller’s own ra with the caller’s callee-saved registers restored. ra values written by helper calls are dead.

  • R4 Memory. Only lw/sw, word-aligned, with these bases:

    • s1: offset in [0, frame_bytes).

    • s11: offset in [0, state_bytes).

    • s0 stores: only the NativeCtx output words (out[0..3], ret_kind, ret_frac, offsets 0..=16). The helper pointer and table are never writable.

    • s0 loads: only lw t0, E(s0) for an exact, aligned helper-table entry E (the generic helper at 24, or a direct entry at 32 + 8·i, i < COUNT).

    No other base is allowed, sp included (it appears only in the fixed sequences), and there are no computed addresses. Every dynamic index goes through a Rust helper that clamps it, exactly like the VM. Region pointers in t6 are planned for buffers but not allowed yet.

  • R5 Helper calls. The only jalr in a body is jalr ra, 0(t0), with funct3 = 0 and offset = 0. It must directly follow an R4 table load. Pointer arguments are pinned by fixed instructions right before the call:

    • Generic helper: addi a0,s0,0; addi a1,s1,WIN; lui/addi a2; lui/addi a3; lw t0,24(s0); jalr. So ctx is the real context and the window is the frame’s helper window. The verifier also requires frame_bytes >= (WIN_OFF+WIN_WORDS)·4.

    • HSV/palette: addi a3,s1,WIN; lw t0,E(s0); jalr. a3 is the blue output pointer.

    • Scalar direct helpers take only scalar words.

  • R6 Control flow. jal must have rd = x0. Branch funct3 must be one of the six real branches. Every branch and jal target must be word-aligned, inside the image, and outside these places:

    • any prologue;

    • an epilogue past its first word;

    • a helper call’s protected window. For the generic helper that is the words after its a1 pin through the call. For a colour helper it is the table load and the call. For a scalar helper it is the call.

  • R7 Budget. Any branch or jal whose target is at or before its own pc (every back edge and loop header) must land on a canonical budget check: addi s10,s10,-n (with 1 ≤ n ≤ 2048), bge s10,x0,+8, jal x0,STUB. STUB is the exact exit stub (out = 0, ret_kind = RET_RET), and the exact epilogue follows it directly. s10 is callee-saved across helpers and written nowhere else (R2). Every other transfer moves strictly forward, and helpers return to pc+4, so every cycle passes through a decrement of at least 1. Once s10 < 0, the next back edge takes the straight-line stub → epilogue → ret. A cycle can’t skip the decrement by entering the middle of a check, because that target isn’t a check, and helper-call return points are not checks either. The lowerer puts a check at the head of every basic block (each branch target is a block header). It refuses a block with more than 2048 ops, which would leave the native budget and the VM’s out of step.

  • R8 Nothing else. lui, OP-IMM and OP (base and M; reserved funct7/shift encodings rejected) are allowed. auipc, ecall/ebreak/CSR, fence/fence.i, AMOs, and all other opcodes are rejected.

Not covered by the verifier, and not an escape: the generic helper’s a2 (opcode) and a3 (operand offset) are image-chosen. The helper reads operands through ctx.code.get() and a WIN_WORDS slice. A crafted pair can make it panic, which is a crash and not a write outside its slices. Images lowered on the device always pass the real pair. Wall-time deadline polling at loop headers is still planned. The instruction budget above is the deterministic bound, and the watchdog stays the backstop.

firmware/fx_aot/src/verify_tests.rs pins each rule with negative tests. That includes the four sandbox escapes the #351 review found (ra, reserved bases, unbounded base offsets, unbudgeted loops), each as the original PoC plus variants, and unpinned helper pointer arguments. The positive side has three parts: fx_aot_diff_test verifies every image it lowers before the bit-exact comparison, native_vs_vm_test verifies every image embedded in the C6 bench, and the bench generator refuses to embed an image that fails.

  • Execution region (W^X): the image is copied into its region while the region is plain data memory, then it is made R+X without W for the run and restored to writable when the effect is swapped out. See “Where native code lives” for how that is enforced in machine mode.

The sandbox doesn’t depend on who produced the code. That matters for the trust options below: option (a) relies on it entirely, and options (b) and (c) use it as defence in depth.

Where native code lives¶

Owner decision (2026-10-23): native code is allocated from the FX arena — the same memory budget the decks’ programs and buffers already use — never from the general heap, so it can never starve TLS or anything else. littlefs only stores a (future, stage 3) prebuilt image; nothing ever executes from flash, and there is no new flash partition. If a translated image doesn’t fit the deck’s arena share, that effect stays on the VM (never heap).

The FX arena is the 24 KB FX_ARENA split per deck (deck A from the front, deck B from the back; firmware/player_app/ffi.rs). A native effect carves a code sub-region at the top of its deck’s share; the effect’s buffers grow from the bottom. fx_aot::arena::plan_region does the placement and refuses (→ VM) when the code plus the buffers don’t fit.

Making arena memory executable and non-writable (W^X), in machine mode¶

This firmware runs entirely in machine mode, where a RISC-V PMP entry that matches grants permission but a locked entry is needed to deny a permission — and a locked entry can’t be changed until reset, so it can’t be re-protected on an effect swap. An unlocked PMP entry therefore can grant execute (as the JIT’s region already does) but cannot take write away.

The ESP32-C6 also has Espressif’s PMA checker (CSRs 0xBC0+n/0xBD0+n, 16 entries; IDF uses 0–12 locked and leaves 13–15 free). A hardware probe (firmware/fx_perf_bench:pma_probe, run on rig-3 c6-117d10, 2026-10-23) confirmed that an unlocked PMA entry (TOR, R+X, no W) denies a machine-mode store to a RAM window while an unlocked PMP entry grants execute on it:

fxpb-pma boot ... win=0x4080e000
fxpb pma exec=42 about_to_store      # executed from the window: OK
Guru Meditation Error: ... (Store access fault)  MCAUSE=0x7 MTVAL=0x4080e800

So an arena code region gets execute from a PMP entry + no-write from a PMA entry, both unlocked so they are cleared on swap/park to restore write for the allocator:

Two NAPOT regions (not one TOR pair) so both decks can be protected at once during a crossfade. NAPOT needs a power-of-two size and a size-aligned base, so FX_ARENA is aligned to the max code region and plan_region rounds the image up to a power-of-two sub-region (4-byte PMP/PMA granularity otherwise). On an effect swap or when a deck parks, the firmware clears that deck’s PMP+PMA entries before reusing the memory, and re-programs them for the new image.

Netstack wiring (stage 3 is a wiring job)¶

The allocation math and the W^X mechanism exist now; the netstack port wires them into fx_load/fx_clear/park in ffi.rs:

  1. on load, after the device lowers (option a) or verifies a signed image (option b), call fx_aot::arena::plan_region(deck_off, deck_len, arena_need(prog), image_bytes); None ⇒ keep the VM;

  2. copy the image words into the arena at code_off, fence.i;

  3. program this deck’s PMP entry (3 or 4) R+X and PMA entry (13 or 14) no-W over [base, base+code_size) using arena::pmp_napot_addr (the same CSR writes as pma_probe/the JIT arming);

  4. on swap/park (fx_clear, deck re-point), clear that deck’s PMP+PMA entries first so the bump allocator can reuse the bytes writably;

  5. the buffers of that deck live below buffers_avail, so arena_need must leave room — plan_region enforces it.

Trust: who may produce native code the device runs?¶

Owner decision (2026-10-28). “Users should be able to sign effects for their own fixtures — we need an efficient way to check those signatures. 4 bytes of an HMAC computed against a user’s provisioned key would be sufficient as a signature. We don’t currently have a provisioning scheme that allows users to ‘pair’ their fixtures so that only their authenticated commands can run, so for now let’s just provision a dev key and get the signature checking infra brought up.” Follow-up the same day: don’t bind a signature to the firmware build (that would invalidate every user’s signed effects on each release). Bind a small native ABI version and a non-downgrade minimum firmware instead, and retire old blobs by key epoch / key revocation.

This replaces the earlier recommendation (“(a) everywhere + a CI-held P-256 native key; per-owner keys rejected”). The reasoning that changed is in “Threat model” below: every image passes the sandbox verifier and runs under arena W^X whoever signed it, so a stolen user key yields sandboxed native code, not arbitrary machine code.

For one effect the device prefers, in order: a valid .fxn for exactly that .fxb (b) → lowering it itself (a) → the VM. Any failure at any step falls through to the next, and the VM always works: an effect never refuses to play because of a signature. What (a) and (b) share, and what the signature never bypasses:

  • the instruction-stream verifier (fx_aot::verify) on every image;

  • placement only in the FX arena (no fit → VM), executed under PMP X + PMA no-W;

  • the instruction budget mirrored into native code.

The signature only decides whether a prebuilt image is considered. (b) exists for code the device can’t or shouldn’t produce itself: a heavier host optimiser, hand-tuned images, or skipping on-device lowering time and transient heap at load.

(c) P-256 first-party images: not needed now. The HMAC path already carries prebuilt images, and there is no first-party native library yet. If one appears that must run on devices sharing no symmetric key with CI, add it as an asymmetric variant of the same container (format version 2 or a flag bit: the header has both) under a key id that is never in the loader ring and never an epoch signer. The earlier role-separation argument for that key still holds. The relay compile-and-sign option stays rejected: an online signing oracle proves nothing that (a) doesn’t.

  • Domain separation: the 16-byte prefix splanc-fx-sig-v1 and the magic and format version inside header[0..36]. A tag for anything else under the same key can’t be replayed here.

  • Everything is bound: every header field (key id, epoch, ABI, min_fw, scope, sizes, entry offsets), the code, the operand bytes, and the exact .fxb. The device already holds the .fxb, so it is hashed, not shipped twice. A blob checked against any other bytecode fails. abi and min_fw sit in the header and in the MAC’d message, so they can’t be relabelled.

  • Not bound: the firmware build. A blob stays valid on every firmware ≥ min_fw that lists its abi.

  • Comparison is constant-time (XOR-fold, no early exit).

  • Host signer: bazel run //firmware/fx_sig:fx_sign -- sign --fxb e.fxb --out e.fxn [--key-file K --key-id N] [--epoch E] [--min-fw X.Y.Z] [--scope fleet|aa:bb:..]. It lowers with fx_aot, runs the verifier, then signs. With no --key-file it signs with the dev key. fx_sign verify checks a blob. The bench generator (firmware/fx_perf_bench/gen_effects.rs, the place this PR produces prebuilt images) signs every embedded image with the dev key automatically.

Firmware version (min_fw): the OTA manifest’s monotonic packing, major * 1_000_000 + minor * 1_000 + patch (1.6.0 → 1006000), parsed from the build’s firmware-v* version (fx_sig::parse_fw_version, the same function as ota_parse_version). Untagged development builds report 0, so they run only min_fw = 0 blobs. Firmware older than min_fw keeps the effect on the VM.

Native ABI (abi, fx_aot::NATIVE_ABI, currently 1) covers everything a prebuilt image hard-codes about the firmware that runs it:

  • the NativeCtx layout and its baked offsets;

  • the direct-helper table order and the generic helper’s (ctx, win, op, code_off) convention;

  • the register/frame layout and the entry calling convention;

  • the budget mirror;

  • the op_code contract.

Bump it when any of those change. A firmware lists the ABIs it can run; any other ABI keeps the effect on the VM. Retiring an ABI is also a blunt revocation lever (every blob of that ABI drops to the VM or on-device lowering).

What the client sees on a fallback. The device reports a stable reason token (malformed, unknown_key, revoked_key, old_epoch, wrong_scope, abi_unsupported, fw_too_old, rate_limited, bad_tag) together with its running fw version and native abi. The bench logs aot <effect> ... ok=0 reason=sig:<token> fw=<n> abi=<n> vm=1. In player_app this becomes a field of the effect-load reply (stage 3).

Why a 32-bit tag is enough, and what makes it so¶

  • HMAC-SHA256 is a PRF. Without the key, the tag of a new message is unpredictable, so a forgery is a guess: success probability 2^-32 per attempt. Seeing any number of valid tags doesn’t help forge one for different code.

  • Guesses can only be checked online, against a device. So the device bounds the rate (fx_sig::Limiter):

    • the first 3 consecutive bad tags are free (developer mistakes);

    • after that each attempt waits 0.5 s, doubling, capped at 60 s.

    • At the cap that is one guess a minute: an expected 2^31 minutes (about 4,000 years) per forgery, about 8 years for a 1-in-500 chance.

  • The limiter is device-wide, not per connection, so new sessions don’t reset it.

  • Its consecutive-failure count is persisted in NVS and re-armed at boot, so a reboot doesn’t reset it either. Writes happen once per failure (bounded by the backoff) and once on the next success.

  • Structural refusals (ABI, min_fw, key, epoch, scope) happen before the limiter and the MAC. They are about public header fields and reveal nothing about the key.

  • The limiter runs before the MAC, so during a backoff even a valid blob is held off (rate_limited) and timing reveals nothing.

  • Every failure is logged (sig reject reason=… boot_fails=…).

  • Cost of a device-wide limiter: anyone flooding bad tags delays legitimate native loads by up to a minute. Those effects keep running on the VM, so this degrades speed, not function.

  • Birthday bounds don’t apply: an attacker can’t evaluate tags offline.

  • A valid blob replayed later is the same code its signer authorised. Retire old blobs with the epoch or key revocation (below), not with a version field. Device-scoped blobs can’t be replayed onto other devices.

Threat model¶

  • Today (dev key everywhere): the signature authenticates nothing. The dev key (fx_sig::DEV_KEY, key id 0, the ASCII string splanc-fx-dev-key-NOT-SECRET-v1!) is in the repository. Anyone can sign anything. What stands between a malicious .fxn and the device is the sandbox: the verifier’s narrow instruction grammar, calls only through the trusted helper table, loads and stores only to the frame/state/output words, the budget, and arena placement under W^X. That is the same bar on-device lowering (a) has to meet. The infrastructure exists so the user-key future is a provisioning change, not a format change.

  • With per-user keys:

    • An attacker on the LAN without the key can submit blobs but faces 2^-32 per guess under the backoff above.

    • An attacker with a user’s key can sign native code for that user’s devices. The key might come from XSS in the app, a malicious MCP client or a compromised agent host. That code is still confined to the sandbox above. So a stolen key yields “whatever the verifier admits”, the same class of risk as a bug in on-device lowering. It does not yield arbitrary code execution, firmware replacement (OTA has its own P-256 ring that this key is never part of), or access outside the effect’s arena region.

    • Recovery: revoke the key id or raise min_epoch. The affected effects keep playing on the VM.

  • Not covered:

    • confidentiality of effects;

    • authenticating the commands that deliver a blob, which is the pairing work below;

    • side channels in the soft SHA. The software path isn’t constant-time with respect to the payload, which is public anyway. The key-dependent part is the precomputed HMAC pads.

Keys, revocation and the provisioning seam¶

  • Key ring (fx_sig::KeyRing): up to 4 keys, each stored as its precomputed HMAC inner/outer SHA-256 states, so a verify skips the pad compressions. Key id 0 is the dev key, compiled in and installed on every device by default. User keys use ids 1..31.

  • Device policy (fx_sig::Policy, persisted, never lowered, like the OTA keyring’s kepoch/krevoked):

    • min_epoch (u16): blobs signed under a lower key_epoch are refused. Raising it retires every older blob at once.

    • revoked (u32): one bit per key id 0..31. Setting bit 0 retires every dev-signed blob once user keys exist.

  • NVS (namespace splanc_fxsig):

    • k1..k3: 32-byte user keys;

    • minep, revoked: the policy;

    • fails: the persisted backoff.

    The bench image reads and writes exactly these. An erased NVS falls back to dev key only, policy 0, no backoff.

  • Provisioning seam (placeholder, not implemented). Pairing must deliver a key over an authenticated channel, never in clear over the LAN. One candidate is ECDH during BLE Improv provisioning, confirmed by physical presence (a button press or a code shown on the fixture). Proposed protocol shape, reusing the Rust API that exists now (KeyRing::install/remove, Policy::raise_min_epoch/revoke):

    • fx_key_status → {key_ids, min_epoch, revoked, fw_version, abis, sig_fails, retry_ms}. Unauthenticated, public facts only.

    • fx_key_provision{key_id, key_epoch, wrapped_key, proof}: install or replace a user key. wrapped_key is encrypted to the pairing session. proof is the pairing transcript’s MAC.

    • fx_key_revoke{key_id | min_epoch, auth}: auth is an HMAC under a currently valid user key (or physical presence), over the request and a device nonce.

    • A load-reply field native: {ok, reason, fw_version, abi, retry_ms} for the fallback report above.

    Migration off the dev key: pair (install key id 1), re-sign the user’s blobs, then revoke id 0. Dev-signed blobs then run on the VM or on-device lowering; they never fail to play.

Decisions needed from the owner before production¶

  1. Pairing scheme for per-user keys: which channel delivers the key (BLE Improv ECDH + physical presence is the proposal), and whether one key per user covers all their fixtures (fleet scope) or per-device keys are wanted.

  2. Whether to revoke the dev key in release firmware once pairing exists (recommended: release builds ship revoked bit 0 set; dev builds don’t).

  3. Backoff parameters: 3 free failures, 0.5 s doubling, 60 s cap, device-wide. Accept, or prefer per-session limits plus a lower global cap.

  4. (c) P-256 first-party images: confirm they stay unbuilt until a first-party native library exists.

  5. Code placement: DECIDED (2026-10-23): the FX arena, never general heap; no flash partition; littlefs stores only. See “Where native code lives”.

  6. Trust model: DECIDED (2026-10-28): user-key HMAC (dev key for now) + unsigned on-device lowering.

Plan¶

  1. Stage 1 (this PR): firmware/fx_aot:

    • static-depth verification and lowering of the integer/fixed and control subset to RV32IM, reusing fx_jit::rv32 read-only (new encodings live in fx_aot);

    • its own RV32IM emulator with a helper-call trap;

    • differential tests against the real fx_vm over the compiler’s corpus, random programs, and budget and edge cases.

  2. Stage 2 (this PR):

    • the helper table: soft-float, maths, colour, vectors, indexed access, buffers/textures, graph;

    • the instruction-stream verifier;

    • an AOT group in the bench image (firmware/fx_perf_bench, static RAM region, unsigned);

    • measured cycles per LED against the VM on a real C6.

    • Small additive change: some private fx_vm maths helpers become pub, so helpers call the interpreter’s exact functions.

  3. Signature infrastructure (this PR): firmware/fx_sig (the .fxn container, 4-byte HMAC tag, key ring + policy, backoff), the fx_sign host tool, dev-key signing in the bench generator, and the bench’s authenticate-then-load path with NVS keys and a persisted backoff.

  4. Stage 3:

    • for (a), on-device lowering in player_app, carving the arena sub-region and programming PMP+PMA per “Netstack wiring” (the allocation math and the W^X mechanism already exist);

    • for (b), the same authenticate step in player_app’s effect load (prefer a valid .fxn, else lower, else VM) with the hardware SHA (mbedtls is already linked), the splanc_fxsig NVS namespace, and the fallback reason in the load reply;

    • pairing / per-user key provisioning per “Provisioning seam”.

  5. Stage 4: a Thumb-2 backend for future boards.

Status, measured numbers, and what is not verified¶

Stages 1–2 landed (this PR). What exists and is verified:

  • firmware/fx_aot lowers verified .fxb to position-independent RV32IM: static CFG depth analysis, slots 0–7 in s2..s9 and deeper slots in a frame, inline integer/fixed/control codegen, dedicated helpers for scalar/lane float maths, comparisons, conversions and colour, plus the generic helper for remaining operations (reusing fx_vm’s own now-pub maths), a per-block budget decrement, and a VM fallback for any unsupported opcode. Buffers, textures, graph queries, flood, I2C, the JIT op and user functions are not yet lowered (they fall back to the VM); user-function cloning per entry depth is the main stage-2 follow-up.

  • The instruction-stream verifier re-checks every emitted image.

  • A differential test (fx_aot_diff_test) proves native output equals the VM bit-for-bit over the compiler corpus + embedded study/agent effects, 64 LED positions × 3 frames, including raw state checks. The current 36-effect corpus has 28 effects lowering and matching and 8 falling back (unchanged by the dedicated-helper follow-up). The bench’s on-C6 aot pass cross-checks every LED against the VM on the real helix.

  • The arena W^X scheme is hardware-confirmed (the PMA probe above).

Dedicated helper follow-up (#351)¶

Compared with agent/fx-aot at f6caeca9b618038204e5f2fa3f06825c1fc5e773:

  • Float Add/Sub/Mul/Div/Neg, unary and binary maths, Clamp/Smoothstep, comparisons/logic, hash, conversions, HSV and palette use per-operation helper entries. Scalar operands move directly from their callee-saved homes into a0..a3; scalar results return in a0. HSV/palette return red/green in a0/a1; blue alone uses one fixed output word because RV32’s C ABI returns at most two words in registers.

  • The fixed-stride table is embedded in NativeCtx, initialized outside the bench timer. On RV32 Add/Sub/Mul/I2F point directly at the compiler-builtins used by the VM (__addsf3, __subsf3, __mulsf3, __floatsisf). Div, comparisons and float-to-int retain small semantic wrappers for zero divisors, float booleans and Rust’s saturating casts. No ROM addresses are baked into images. The context grows by 344 bytes on the host and 348 bytes on RV32 (including alignment padding; 408 bytes total on RV32).

  • Scale and Mix deliberately retain the generic helper. Dedicated versions changed NaN payload selection after optimization. Vector reductions and cross/normalize, fixed-point complex operations, context/uniform/indexed operations also retain it. Buffer/texture/graph/flood/user-function support remains follow-up work; I2C and JIT calls still fall back to the VM.

  • Verifier additions (since tightened into the “Verifier rules” above): calls must follow an exact aligned table-entry word load; no branch/jump may enter a helper call after its load; branch/jump offsets must be word-aligned; jalr must have funct3/offset zero; context stores may address only the five output words, never the helper table. Negative tests cover table bounds/padding, load width, call offsets, bypassing loads and writes into the table. Arena/PMP/PMA policy is unchanged.

  • The host emulator now clobbers caller-saved registers at calls and reports emitted instruction/helper-call counts. Counts exclude helper bodies, soft-float routines and hardware timing. More lane helpers can mean more calls despite fewer emitted instructions; this is not a C6 speed claim.

  • The new raw-word host differential tests signed zeros, subnormals, infinities, quiet/signaling NaN payloads, conversion boundaries, lane widths 1–4 and live stack prefixes at depths 0/7/8/13: 492,096 comparisons in opt. Debug mode skips only inputs where the baseline VM itself panics (existing overflowing sqrtf/expf arithmetic); returning inputs still compare exactly.

  • tests/run_rv32.sh runs the actual RV32 VM and helper machine code plus emitted images under QEMU user-mode, with Rust 1.85.0 and the riscv32imac-unknown-none-elf target. 521,920 raw comparisons pass, also covering the retained Scale/Mix path. It needs an installed Rust target and qemu-riscv32; it downloads nothing and accesses no rig. This verifies the integer register ABI and target soft-float, not C6 timings or peripherals.

Both AOT Bazel tests, native_vs_vm_test, the host fx_aot_nostd build and bazel build -c opt //firmware/fx_perf_bench:fx_perf_bench_flashbundle pass. The RV32 no_std crate links and executes in the QEMU test.
