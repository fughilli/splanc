Matter on the lamp’s ESP32-C6 (port spike, D-189)¶

Status: spike. This doc has measured numbers and a recommendation. No Matter code is in the player yet. Owner decision D-189: “Start a port spike now” and “We should be able to fit this.” The smart-home study (docs/design/smart-home-integrations.md §3, PR #582) said Matter does not fit today’s C6 image. This doc tests that claim by measuring instead of estimating.

The answer in one paragraph. It fits, but not by adding Espressif’s SDK. The C++ CHIP SDK (esp-matter) needs ⟦ESPM_FLASH_KB⟧ KB of flash for a size-optimised light (§3). Today’s image has 68 KB left under the layout_test gate, with the mesh in. A Rust Matter stack (rs-matter, no_std, no heap to speak of) needs about 400 KB for the same light, BLE commissioning included (§4). Today’s image also still links about 290 KB of code it never runs (§2.2). The largest piece is the whole lwIP stack, 130 KB, which the netstack replaced. Cutting that dead code, using our mbedTLS in place of RustCrypto, and adding IPv6 (link-local + SLAAC, ND, MLD, UDP) to the netstack makes room for Matter in the existing 2.25 MB app slot, with a margin of ⟦B_MARGIN⟧ KB. Option (a), CHIP next to the netstack, overshoots the slot by ⟦A_OVER⟧ KB after the same cuts. It also needs a second IP stack demuxing our MAC. Option (c), a separate Matter image, cannot fit a third app slot in 4 MB. It would also stop the effects. Recommendation: (b), rs-matter on the netstack, in five milestones, about 6–8 weeks of focused work (§6). The first milestone is the size diet: about two weeks, and the image is better for it whatever happens to Matter. A PoC (§7) commissioned a stock esp-matter light on a rig-2 C6 from this container and toggled it. That gave the real heap profile of a Matter session on this chip.

So the Matter stack itself costs about 400 KB of flash: 442 KB minus the 35 KB platform and the 7 KB QR code. With RustCrypto swapped for our mbedTLS it is about 360 KB, plus the glue to the netstack (§5.2, about 15 KB).

RAM: .bss is 71 KB, but the Matter state is the 51 KB MatterStack cell: 5 fabrics (the spec minimum), sessions, exchanges, the 1,583-byte RX/TX buffers, subscriptions, 3 Wi-Fi networks, BTP. The async tasks’ futures add about 12 KB, and a 4 KB heap covers rs-matter’s small alloc use. The defaults are sized for a hub-class node. For one lamp with one or two controllers, the features max-fabrics-*, max-exchanges-per-session-*, fewer subscriptions and one network bring it to an estimated 30–40 KB. CASE needs about 2 KB of stack for P-256 on top. The spec requires 5 fabrics for certification, so a certified lamp keeps 5 (§8).

5. The three ways to put Matter on the lamp¶

5.1 (a) The CHIP SDK on lwIP, next to the netstack¶

What it takes:

  • lwIP has to run again, fed by our MAC. The netstack owns the RX ring and does its own MLME and WPA (radio_bringup, netstack_transport.cpp:1820). The vendor Wi-Fi driver never associates, so esp_netif’s Wi-Fi glue has nothing to attach to. We would write a custom lwIP netif: linkoutput into the netstack’s tx_l2, and an RX demux in handle_l3 that hands IPv6 frames and UDP 5540 to lwIP. Two IP stacks then share one MAC address, and ARP/ND, DHCP and mDNS have to agree on who answers.

  • The CHIP ESP32 platform layer assumes esp_wifi events, esp_netif, the default event loop and NVS. It needs a new CHIP platform for us (connectivity manager, network commissioning driver, KVS), as an “external platform” (ext_plat).

  • esp-matter v1.5 builds against IDF v5.5.5 with its own sdkconfig. Our IDF is the prebuilt Arduino SDK v5.5.4 with a frozen sdkconfig. CHIP would have to be built against that frozen config, by hand, outside esp-matter’s CMake.

  • Size: ⟦A_SIZE⟧.

  • RAM: ⟦A_RAM⟧.

Verdict: does not fit, and it is the most fragile of the three. It brings back the vendor heap the RAM audits removed. It also adds a second, unaudited stack in front of the radio.

Two netstack rules this has to respect:

  • Group-addressed TX while wss is live drops the wss session (netstack_transport.cpp:808). The mDNS announcements and MLD reports are multicast. Today mDNS answers unicast when a wss session is up. Matter needs the same rule: unicast (QU) answers during a session, announcements only between sessions. Better still, find and fix the root cause in the TX path. That is a prerequisite, and it needs its own HITL gate.

  • The Rust toolchain. rs-matter needs Rust ≥ 1.92. MODULE.bazel pins 1.85.0 for the C6, so the toolchain has to move up. That touches every Rust crate, so it is a PR of its own with the full HITL lane.

Size: 360 KB (rs-matter with the mbedTLS backend) + 15 KB glue = about 375 KB. After the §2.2 cuts there are 255–300 KB left. So it is short by about 75–120 KB. The gap closes in one of these ways (owner decision §10):

  1. Trim rs-matter to what one lamp needs: no QR code (7 KB), no Wi-Fi network commissioning cluster when Improv owns credentials (on-network commissioning only), no BTP when there is no BLE commissioning (12 KB), the IM features a light never uses (events, timed requests on non-lock clusters, the Groups key cluster beyond the mandatory stubs). Estimated 40–70 KB. Some of this needs upstream feature flags; rs-matter is small enough to carry patches.

  2. Grow the app slot. The loader holds 1,300,704 B in a 1,376,256 B slot. It also links the dead lwIP (it is the same netstack build without the player). With C1–C4 it drops to about 1.08 MB. Moving the loader/littlefs/app boundaries by 192 KB needs a one-time partition-table migration. The loader can do it the way it already migrated littlefs (docs/design/ota.md “Migration”), but it is the riskiest step in this plan.

  3. Build Matter as an opt-in feature at first: “Matter” images for lamps that want it, with one of the bigger features left out (see the decision).

RAM: 30–40 KB of Matter state, trimmed (§4). The running image has 93 KB free with the mesh off and 49 KB with the mesh on. Matter and the mesh do not both fit at the 2048-LED max config (29.7 KB minimum today). Matter’s state can share the mesh’s arena: both are heap blocks that are allocated when the feature is switched on (the mode-union design in the RAM audit). Or the two features can be exclusive at max LEDs (owner decision §10). CASE runs inside the TLS region’s budget: P-256 is already there for TLS. Releasing BLE after commissioning returns 33–43 KB (fug71-device-heap-ble). The heapless host makes that smaller on the netstack, but it is still there.

Verdict: fits, with the §2.2 cuts plus one of the three gap closers. It is a sizeable port, but every piece sits on code we already own and test.

5.3 (c) A separate Matter-mode image (OTA slot / partition)¶

  • No room for a third slot. 4 MB = 64 KB (boot/table/nvs/otadata) + 1,344 KB loader + 384 KB littlefs + 2,304 KB app. A Matter image of ⟦ESPM_FLASH_KB⟧ KB (§3) needs its own slot. The only way to get one is to drop littlefs (the map and effects) or the loader (OTA recovery).

  • A Matter image in the app slot instead (the user picks “Splanc” or “Matter” firmware, and the loader switches between them): a lamp in Matter mode has no effects, no app control and no mesh, just a dimmable white light. That breaks “effects keep running” and the product.

  • What (c) is good for: this spike’s PoC. A stock esp-matter light in the app slot proves commissioning and the heap profile on our exact chip (§7). It is also a fallback if (b) slips: a factory-test or certification-lab image.

Verdict: not a product path, but the right tool to measure with.

8. Commissioning without BLE¶

The lamp is already on Wi-Fi after Improv. Matter allows on-network commissioning: the device advertises _matterc._udp with the commissioning window open, and the QR / manual code says DiscoveryCapabilities = OnNetwork. That saves CHIPoBLE (≈ 14 KB with BTP) and keeps one owner for the Wi-Fi credentials (Improv; the “fresh join” rule). The catch: Apple Home and Google Home support on-network commissioning, but their certification programmes expect BLE for Wi-Fi devices that are not yet on a network. A lamp that is always onboarded through the Splanc app is always on the network first. Needs checking against each ecosystem’s current rules (M4).

9. Mapping On/Off and Level onto lamp power¶

The lamp-power work (branch agent/lamp-touch-power, docs/design/lamp-power.md there; protocol arms set_power 130, get_power 131, set_power_config 132, push power_state 70) is the seam. On-lamp Matter calls the same state machine (firmware/power, Machine::request) that set_power does, with a new request source MATTER. It uses the same mapping as the bridge (PR #600, agent/src/bridge/matter.ts), so a lamp behaves the same through either path.

10. Owner decisions¶

  1. Go ahead with M0 (the size diet) now? It frees about 185–235 KB with no Matter code. Options: yes (recommended) / after the mesh settles / no.

  2. How to close the last 75–120 KB for Matter (§5.2). Options: trim rs-matter to a lamp’s needs (recommended first) / grow the app slot with a one-time partition migration / ship Matter as an opt-in image.

  3. Commissioning transport. Options: on-network only at first, BLE (CHIPoBLE) in M3 if an ecosystem needs it (recommended) / BLE from the start.

  4. Matter + mesh at the 2048-LED max config. Options: one shared arena for the two feature states (recommended) / mutually exclusive at max LEDs / cap LEDs when both are on.

  5. Fabric count. Options: 5 (the spec minimum, needed for certification; recommended) / 2–3 for an uncertified first release (saves RAM).

  6. Rust toolchain bump to ≥ 1.92 for the whole firmware (needed by rs-matter). Options: yes, as its own PR before M2 (recommended) / vendor an older rs-matter (0.1.x, much larger, unmaintained).

11. Risks and open questions¶

  • rs-matter is young (v0.4.1). Its CASE/PASE and IM have passed parts of the Matter test harness upstream, but not certification. Budget time for conformance fixes.

  • IPv6 multicast through home APs (snooping, multicast-to-unicast) is where Matter devices fail in the field. M4 has to test on real APs, not only the rig’s hostapd.

  • The group-addressed-TX rule (§5.2) has to be root-caused, not worked around.

  • Our CHIP numbers (§3) come from IDF v5.5.5 + esp-matter v1.5 with their own sdkconfig, not our frozen v5.5.4 SDK. The difference is small next to the gap.
