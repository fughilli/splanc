Lowering the FX engine onto GPUs and accelerators¶

Status: design + host feasibility prototype (this PR). No device code ships. The prototype (//fx_gpu) lowers a meaningful subset of the effects IR to GLSL ES 1.00 / 3.10 + SPIR-V and proves, against the real fx_vm over the test corpus, that the lowering is numerically faithful within tolerance. Pi and P4 work is staged behind owner decisions (end of doc).

Background: fx-perf-study.md, fx-native-aot.md, fx-memoization.md, and the fx_vm module docs. The VM is and stays the semantic reference; everything here is a translation of the .fxb bytecode it already runs, checked against it.

Why¶

The study’s headline: through the VM a non-trivial effect costs 5–35 k cycles per LED on the C6, and at 2048 LEDs only a solid fill fits a 33 ms frame. The AOT path (PR #341) buys 3–20× on the same core. The GPU is a different lever: Splanc MAX already carries a Raspberry Pi whose VideoCore/V3D GPU sits idle while the CPU runs the VM. An effect is a per-LED kernel — embarrassingly parallel across LEDs — which is exactly what a fragment/compute shader is for. On Pi 4/5 a V3D compute pass over 2048 LEDs is a sub-millisecond job; the only real questions are which of the kernel maps to the GPU, how close the GPU’s float gets to the VM’s soft-float, and how the result gets back out to the FPGA/SPI LED path without the readback eating the win.

This document answers those, with a working prototype and measured conformance numbers, and surveys the ESP32-P4 accelerators as a separate (non-GPU) track.

1. Partitioning: what maps to the GPU, what stays on the CPU¶

An effect is update() (once per frame, evolves state) + shade(led) (once per LED, returns RGB) + optional buffers/textures/graph/user-functions. The GPU target is shade() only, as a per-LED kernel. update() stays on the CPU: it is one invocation per frame (not hot), it is where state is written, and it is where sensors/I2C and graph/flood sweeps live.

How the split is wired (the prototype’s model, extends to the device):

  • Per-effect kernel extraction. The CPU loads the .fxb, runs update() and the per-frame prep, then hands the GPU a kernel that is purely shade(uniforms, state, led_attrs) -> rgb. One kernel per loaded effect (two when two decks are active — §”decks”).

  • Uniforms in a UBO/SSBO. uniforms[], the read-only state[] snapshot, the frame context (time/dt/frame/imu/room box) and the CPU-hoisted values go in one std430 buffer, rebound per frame (a few hundred bytes).

  • LED positions as a buffer, one invocation per LED. led.pos/uv/s/idx/seg/ dist/room and their Q16.16 mirrors are a per-LED record in an SSBO (compute: indata[gid*stride + k]) or a 1×N data texture (GLES2 fragment). These are computed once at map load, exactly as the VM’s per-LED fixed cache already is, and only re-uploaded when the map changes.

  • Output. The kernel writes one packed RGBA8 word per LED to an output SSBO (compute) or gl_FragColor into a 1×N RGBA8 render target (fragment). The CPU reads that back and frames it for SPI/FPGA (§4).

2. IR → SPIR-V / GLSL codegen¶

The prototype defines a small kernel IR (fx_gpu/src/ir.rs): a hash-consed (CSE’d) SSA DAG of 32-bit-word nodes, each typed F (f32) / U (32-bit int) / B (bool). Two layers:

  • Macro ops carry exact fx_vm semantics (MDiv0 = divide-by-zero→0, MHash3 = the VM’s bit-mixing hash, MMulFix = Q16.16 multiply, MSel = if-converted branch). lower.rs abstract-interprets the .fxb shade() body into macro ops: it mirrors fx_vm::run op-for-op but over node ids, so the correspondence is auditable. Branches are if-converted (fork both arms to their Ret, merge with MSel on the predicate — exact because shade is side-effect-free).

  • Primitive ops are what a shader expresses directly. legalize.rs rewrites each macro op into primitives for a numerics profile (§3), reproducing the matching fx_vm helper inline (e.g. clamp01’s NaN rule, normalize’s len>1e-9 guard, the mix32 avalanche hash, Q16.16 (a*b)>>16 via mul+mulhi+shift). Only primitives reach the emitters.

Emitters. emit_glsl.rs walks the primitive DAG to SSA statements:

  • Target::Es310Compute — GLSL ES 3.10 compute, 64-wide workgroup, inputs from a std430 float SSBO (int inputs reinterpreted with floatBitsToUint), RGBA packed to a uint output SSBO. Real 32-bit ints → hash/fixed exact. This is the Pi 4/5 path and the SPIR-V source.

  • Target::Es100Fragment — GLSL ES 1.00 fragment, one fragment per LED, gl_FragColor. No integers on VideoCore IV, so a graph needing an int op is refused (Err) and the effect stays on the VM / an int-capable tier (§Tiering).

SPIR-V. The prototype does not hand-write SPIR-V; it emits GLSL ES 3.10 and lets glslang -G produce SPIR-V, validated by spirv-val — the exact toolchain td-deploy uses (compiler/translate_gles.py), and the path Pi V3D’s v3dv consumes. For the production backend use naga (wgpu’s IR): it ingests our module (or a WGSL/GLSL print) and emits SPIR-V, GLSL ES 1.00/3.10 and Metal/HLSL from one place, with validation built in. naga is the recommended crate; rspirv is the fallback if we ever want to emit SPIR-V directly without a GLSL hop. We keep the GLSL ES 1.00 emitter regardless, because naga’s GLSL-100 output for VideoCore needs the same int-free guarantees we already enforce. (Neither crate is in the repo’s offline Bazel universe yet; adding naga is a MODULE.bazel change staged for the device PR.)

3. Numerics policy (owner decision)¶

The GPU’s float is not bit-exact with the VM’s. The VM is deterministic soft-float with deliberately crude helpers: sinf is a 256-entry LUT + lerp, atan2f/expf/logf/powf are low-order polynomials, f2i/floor are bit-twiddles. A GPU computes sin/exp/etc. in hardware to its own (often mediump on VC4) precision. So a GPU tier cannot be a drop-in replacement under the “bit-exact across host and device” rule the current tests assume.

The policy is a three-class conformance model, enforced per numerics profile and measured over the corpus (§Prototype):

  1. Exact (must match bit-for-bit), reproduced on int-capable targets. The integer/fixed world: Hash1/Hash3 (the mix32 avalanche — pure 32-bit int ops), the integer compares, MulFix/*FixN, f2i, rescales, and the RetRgb8/RetRgbFix/unit_u8 quantization. The prototype reproduces these as the VM’s exact integer sequences and the harness confirms 0 error. These require real integers → GLES 3.1 / SPIR-V only (Pi 4/5). On GLES2 they can’t be made exact, so an effect that uses them stays on the VM / an int-capable tier.

  2. Tolerance-bounded (native transcendentals). sin/cos/floor/fract/exp/ log/pow/atan2/sqrt and float divide map to GPU builtins. These differ from the VM’s approximations, but for the vast majority of effects the visible result is within a small 8-bit tolerance. Decision needed: set the per-tier tolerance. Proposed: ≤ 2 / 255 max channel error on Pi 4/5 (highp), ≤ 6 / 255 on Pi 3 (mediump), as golden tests per tier.

  3. Must-emulate-exactly-or-refuse. A few effects are dominated by a transcendental where the VM’s approximation and the hardware’s diverge enough to see (notably tan near its asymptote, and heavy pow/log stacks): measured max error up to the full 255. For these the options are (a) keep them on the VM, or (b) emit the VM’s own approximation in the shader — the LUT sine as a constant texture, the exact polynomials inline — so the GPU reproduces the VM bit-closely. The prototype flags these; the recommendation is (b) for sin/cos (cheap: a 257-entry LUT, and it makes the common case exact too), (a) keep on VM for tan/pow/log -heavy effects until measured need.

Measured conformance (prototype, --profile exact, 64 LEDs × 6 frames, max abs channel error vs fx_vm, 0..255):

  • 132 of 197 corpus effects lower; 125 (95%) are within 2/255; integer hash is exact (0).

  • The 7 over tolerance are all transcendental-stress microbenchmarks: tanM/tan2M (255, tan asymptote), sparkle (245), powfM/powf2M (43), logfM/logf2M (14). Every one is a known class-3 case, not a lowering bug.

The policy keeps the VM bit-exact as today; a GPU tier is opt-in per effect and gated by its measured tier tolerance, with class-1 work staying exact.

4. Readback and the FPGA/SPI path; frame budget¶

The GPU result must reach the Tang FPGA over SPI (the pi/player_rs sink, wire::FpgaCodec). Two transports:

  • Readback (recommended first). glReadPixels (GLES2) / an SSBO map (compute) pulls the 1×N RGBA8 (≈ N×4 bytes; 2048 LEDs = 8 KB) to CPU, the player repacks to the FPGA codec and writes it over spidev exactly as today. Bandwidth is trivial; the cost is the pipeline drain (glFinish), which on VideoCore is sub-ms to a few ms and must be measured (open item — see Prototype/HITL). Keep the readback small: render an LED-count target, never a full screen. Do GRB order + gamma + brightness in the shader so the readback is nearly the SPI payload. PBOs don’t exist in GLES2 and buy little at these sizes; on GLES3 a persistent-mapped SSBO with a fence avoids the full stall.

  • Direct scan-out (later, if readback is the bottleneck). Render the LED grid to a KMS plane and let the display controller stream it to the FPGA over DPI (24-bit parallel RGB) — no CPU readback, and vsync gives exact frame sync. Costs: DPI uses GPIO 0–27 (collides with SPI0/I2C), needs ~28 FPGA input pins and a faked display mode, and requires proving 1:1 pixel values (no plane scaling/dither). SMI (bcm2835-smi) is a middle option but still needs a CPU-visible buffer, so it doesn’t avoid readback. The prior-art baseline (§7) used plain SPI at 15.6 MHz and never needed this.

End-to-end scaling model, 500 LEDs → 20 × 1024 (MAX target)¶

Per frame the stages are: render (GPU or VM) → readback → SPI to the FPGA → FPGA streaming → WS wire. SPI, FPGA and wire run concurrently with each other: the core streams while SPI is still arriving. They’re decoupled from render by the player’s render thread. The frame rate is set by the slowest stage: fps ≈ 1 / max(render + readback, SPI, wire).

Wire (hard ceiling). Per channel, L LEDs × 3 bytes × 9.963 µs (the core’s 54 MHz bit period of 1.2407 µs, plus 2 clocks per byte) + 80 µs latch. All channels run in parallel, so this depends only on LEDs per channel.

FPGA FIFO (#370): with SPI at r × the drain rate, each port’s FIFO peaks at about 3L·(1 − 1/r) + PREFILL bytes. The in-tree core has 1,659 B/port (553 LEDs); #370’s 20-port variant has 2,048 B/port.

SPI. One frame is 3N + 1 bytes in a single spidev write (CS low for the whole frame; CS-high latches). It must sustain ≥ the drain rate channels × 0.803 Mbit/s and finish within the wire time. The player asks for min(2 × channels × 0.8 MHz, 24 MHz).

  • The Pi 3’s SPI clock is core_clk / even divisor. At 400 MHz the 24 MHz request rounds to ~22.2 MHz (/18; to confirm on the capture).

  • So 20 channels run at r ≈ 1.38 over the 16.06 Mbit/s drain. The FPGA sim (#370) passes 16.7–27 MHz with peak FIFO fill ≈ L·(1−1/r).

Where the bottleneck sits.

  • GPU: the wire, at every scale. Render + readback uses ≤ 11% of the 30.7 ms frame even at 20×1024. SPI (22.1 ms at 22.2 MHz) also fits under the wire, concurrently.

  • VM on one core: fine through 4×1024. From 8×1024 the heavier effects become the bottleneck. At 20×1024 every non-trivial effect misses the 32.6 fps ceiling: cylinder 37.5 ms, pulses 33.3, plasma 51.9, noise 108.

  • VM on four cores (estimate): this would fit everything measured under the wire except noise (~31 ms, borderline), at the cost of all four cores. The per-thread VM bench is in the payload (--vm-threads 1,4); host scaling measured 3.4–3.7× on 4 threads.

MAX image changes this needs (proposals)¶

  1. spidev.bufsiz: handled by the MAX OTA PR #369. spidev rejects any single write larger than bufsiz (default 4,096 bytes). The player writes each STREAM frame in one write_all, which must stay one transfer because CS-high latches. So on main every frame over 1,365 LEDs fails, including today’s 4×550 (6,601 bytes). #369 found that this failed silently with EMSGSIZE and makes the error visible. Its image sets spidev.bufsiz=65536, which covers 20×1024 (61,441 bytes). #369 also fixes a player crash-loop on main (stack overflow in an 8 MiB thread). Nothing more is needed here beyond landing #369. Above 21,845 LEDs the codec would have to split frames with CS held, which write_all can’t do. The bcm2835 SPI DMA handling a single 61 KB transfer is to verify on the #369 test image (the planned SPI-tap capture on pi-ledmapper-1).

  2. Pin the VideoCore core clock on the Pi 3. The Pi 3’s SPI clock divides core_clk, which drops with frequency scaling (400 → 250 MHz). That would take a 22.2 MHz SCK down to ~13.9 MHz, below the 20-channel drain. Set core_freq=400 + core_freq_min=400 (or a fixed 250 with the divider retuned) in config.txt. This matters only from ~16 channels up, but it silently breaks frames when it does.

  3. 20 channels on the FPGA: the in-tree Tang Nano bitstream drives 8 outputs (NUM_WS = 8, ws[0..7] on pins 70–77) with 553 LEDs/port FIFOs. 20 × 1024 needs MAX_PORTS = NUM_WS = 20, 12 more .cst pins (Tang Nano 9K header I/O to be chosen), FIFO_DEPTH = 2048 (one BSRAM/port; full-frame FIFOs need 40 of the 26 BSRAMs), and SPI ≥ 16.7 MHz. Draft #370 adds that variant internal-only (no pin map) and verifies it in place-and-route (2145 LUT4, 1415 DFF, 20/26 BSRAM, 83 MHz vs 54) and in a 20×1024 Verilator sim. It also fixes the core README’s stale “~2 bytes of buffer per port” claim; the core has had per-port BSRAM FIFOs since the double-buffer was replaced.

  4. Start-of-frame gap guard. The FIFOs absorb mid-frame SPI pauses of hundreds of µs. Right after a frame starts, though, the only slack is PREFILL × 10 µs (20 µs by default), and a longer Pi-side pause latches the strip mid-frame. PREFILL = 64 absorbs 600 µs at zero resource cost (sim, #370). It needs the one-LUT “start on CS-end” fix for frames under 64 bytes/port. The SPI-tap capture on rig-1 will show whether the Pi 3 actually pauses there.

5. Measured speedups: Pi 3B+ (VideoCore IV), GLES2 vs the VM¶

Run 1 setup:

  • fx_gpu/pi3bench on pi-ledmapper-2 (Pi 3 Model B Plus Rev 1.4, kernel 6.12.87, stock pi-v1 MAX image), one reservation.

  • The image has vc4 KMS on (dtoverlay=vc4-kms-v3d, render node present, CMA 256 MB). It ships no Mesa of its own, so the payload’s lean Mesa was used.

  • Renderer “VC4 V3D 2.1”, OpenGL ES 2.0 Mesa 26.2.4: max texture 2048, 8 vertex attributes.

  • The player was running, at load 1.0 and 1.3 GHz.

The VM reproduced the host goldens with 0 errors on every point, confirming cross-platform bit-exactness on real hardware.

What the numbers say:

  • GPU time is set by LED count, not the effect. Render is 1.50–1.73 ms at 20k LEDs, from solid_fill (3 IR nodes) to plasma (54). vc4’s per-vertex fixed cost dominates, and kernel ALU is noise at these sizes. So the GPU cost is flat: ~0.08 µs/LED render + ~0.07 µs/LED readback. The VM’s is 0.33–5.3 µs/LED.

  • Readback is cheap but not free: 1.4 ms for 80 KB at 20×1024 (~58 MB/s, a synchronous glReadPixels from the tiled framebuffer).

    • The driver’s preferred read format is RGBA8, so no faster format exists.

    • An RGB565 target halves readback to 0.65 ms but makes render slower (2.3–3.4 ms) and is lossy. Not worth it.

    • Pipelined draw + read (no explicit glFinish) is 3.2–3.5 ms.

  • Accuracy is well inside the Pi 3 tolerance proposed in §3 (≤ 6/255): max 2/255, and 100% of LEDs within 2. Effects built on float add/mul/compare are bit-exact on vc4. The 1–2/255 differences come only from native sin/divide (class 2).

  • Speedup at 20×1024: 2.1× (solid fill) to 14.8× (plasma) end to end. At today’s 4×550 the GPU is 0.62 ms against a VM 0.70–5.6 ms (11.6 for noise), both far under the 16.5 ms wire. At today’s scale the GPU isn’t needed; at MAX scale it is the only Pi 3 path that keeps non-trivial effects at the wire ceiling.

  • VM threading: fxvm_bench (and today’s player) runs the VM on one core. A 4-thread split (now fxvm_bench --threads; LEDs are independent and update/prepare are per-frame and tiny) measured 3.4–3.7× on the host. On the Pi 3 I estimate ~3.5×, which needs confirming with --vm-threads 1,4: plasma ≈ 15 ms and noise ≈ 31 ms at 20×1024. That uses all four cores, which the player, networking and the Pi 3B+’s thermal throttle share. The GPU path leaves the CPU free: render + readback mostly waits on the GPU, though CPU time on that path was not measured.

  • Pi 4/5 (V3D compute) is not measured here. Expect the same flat per-LED cost at a fraction of vc4’s, plus exact integer ops, so hash effects run there too.

GLES2 coverage: what still can’t go to the Pi 3 GPU¶

Of the 132 corpus effects that lower, 100 run on GLES2 / vc4. The hsv fix moved cylinder-style effects across; it had been 92. All remaining 32 are blocked by hash: noise, noise_field, pulses, sparkle, segment_pulses, rain_naive and others. The VM’s hash is an integer avalanche (mix32) over the operand’s f32 bit pattern. GLSL ES 1.00 has neither integers nor bit casts, so it can’t be expressed there. The other 65 corpus effects don’t lower at all yet (buffers/textures, unimplemented fixed ops, loops, user functions; §1) and stay on the VM on every tier. Options for the hash class:

The fallback is the VM, which is why correctness is never at risk: an effect is promoted to a GPU tier only when (a) it lowers, (b) the target supports its ops (GLES2 rejects integers), and (c) it passes the tier’s golden tolerance. Anything else runs on the VM exactly as today. A per-effect probe at load time (lower → legalize → tolerance-check against a VM reference pass over the map) decides this; the result is cached with the compiled effect.

NEON/native CPU path: the AOT translator (firmware/fx_aot, #341) already targets RV32 for the C6. The same bytecode→native lowering retargeted to aarch64 + NEON gives the Pi a fast CPU tier for effects that don’t go to the GPU (buffers, user functions, loops). That is a separate workstream; the GPU tier and the VM fallback stand on their own.

7. Prior art: ledsuitdisplaydriver + ledsuit-fpga (2019–2020)¶

Two of the user’s earlier repos drove ~900 WS2812B LEDs from GPU visuals on a Pi 3 + FPGA. The user’s framing: “an existence proof, but not a guaranteed-best method.” Key finding from reading them: the Pi side did NOT run a per-LED GPU shader. It captured a separately-rendered window with the Broadcom DISPMANX snapshot API (vc_dispmanx_snapshot + vc_dispmanx_resource_read_data in vc_capture_source.cc) into an RGB888 CPU buffer, then point-sampled it per LED on the CPU from a 50×50 raster (led_driver.cc, nearest-neighbour via x*(w-1)). The README itself calls out “extreme spatial aliasing from the sampling scheme.” CPU post-processing did threshold, a crude power limiter, gamma 2.8, and GRB swap.

  • Transfer: /dev/spidev0.0, mode 0, 15.6 MHz, one burst per frame; framing is a 2-byte [w|addr15] header + raw bytes auto-incrementing into FPGA BRAM (spi_memory.v). 900×3 bytes ≈ 1.39 ms on the wire (computed), ~10× headroom.

  • FPGA (ledsuit-fpga): iCE40 LP8K (TinyFPGA BX, yosys/arachne-pnr), SB_PLL40 to 50 MHz, an SPI slave into a single BRAM frame buffer (7,200 bytes), a priority bus_arbiter, and 8 parallel strip_driver WS2812 engines (300 LEDs each, 1,400 ns/bit). Computed refresh ≈ 11.1 ms ≈ 90 Hz per 300-LED strip, all strips in parallel. The strips free-run from the buffer.

  • No measured fps/latency in either repo; every number above is computed from constants. No frame sync: render, capture, SPI and strip refresh are four free-running clocks; the single-buffered BRAM can tear mid-strip.

Keep: the Pi-renders / FPGA-owns-timing split; the free-running parallel WS2812 engines; the address+burst SPI framing; channel-major memory layout (strip k at base k×LEDs); mapping data kept separate from the renderer; gamma + per-channel peak-brightness calibration + a power limiter (port as shader math or an FPGA LUT).

Do differently, with reasons:

  • Evaluate effects per LED; don’t sample a picture. Splanc effects are functions of each LED’s position, so render one fragment/invocation per LED (FBO width = LEDs/channel, height = channels; each row = one strip’s address range). This removes the aliasing and the CPU sampling loop. Our prototype is exactly this per-LED kernel.

  • Surfaceless EGL over GBM//dev/dri, not X11 + DISPMANX. DISPMANX is a firmware API that only works under legacy/fkms and is gone under full vc4-kms-v3d on current Pi OS. td-deploy’s surfaceless-EGL path (§Toolchain) is the supported route and needs no display.

  • Do GRB/gamma/brightness on the GPU so the readback is nearly the SPI payload (they did it on the CPU).

  • Double-buffer in the FPGA + a commit/swap on CS-rising and a frame sequence number + CRC in the header — the old single-buffer tore.

  • Pace to one clock (FPGA “ready” GPIO or a timer), not four free-running loops.

  • Mind SPI limits: spidev’s default bufsiz is 4 KB, so ≥1366 LEDs needs chunking or a module param; and the FPGA’s SPI oversampling margin is ~clk/4, so check before pushing SCK past ~12 MHz.

Readback vs direct scan-out is weighed in §4. The existence-proof baseline to beat: ~1.39 ms SPI/900 LEDs and ~90 Hz WS2812 refresh/300-LED strip.

8. Pi toolchain: reuse from td-deploy¶

td-deploy already solved the hard image/toolchain parts; reuse directly (/workspace/.claude/siblings/td-deploy):

  • deploy/nix/mesa-lean.nix — Mesa restricted to galliumDrivers=["vc4" "v3d"] + vulkanDrivers=["broadcom"] and, the load-bearing part, -Dllvm=disabled (plus rusticl/vdpau/va/xa/teflon off). This is what keeps the 507 MB LLVM out of the image (td-deploy’s whale). Reproduced on this host in this PR: a lean Mesa 26.2.4 with vc4+v3d+broadcom and zero LLVM in the closure. Mesa itself is 35 MB on disk (an earlier draft said 118 MB, a misread of the closure size). The whole relocatable runtime set (Mesa + libglvnd + libdrm + X/wayland client libs + glibc) is ~125 MB, ~37 MB compressed. In an image that already ships glibc, Mesa adds ~40–60 MB. Mesa 26 needs extra knobs vs td-deploy’s pin (-Dtools=, -Dvideo-codecs=, -Dvulkan-layers=, install-mesa-clc/install-precomp-compiler/intel-rt off, no gallium-vdpau/xa options, and dropping the rusticl postFixup); captured in fx_gpu/pi3bench/mesa-lean.nix.

  • Surfaceless EGL context (runtime_rs/src/main.rs make_gl): eglGetPlatformDisplay(EGL_PLATFORM_SURFACELESS_MESA), dlopen libEGL via khronos-egl’s dynamic feature, no display; target chosen per board (gles2 for vc4, gles ES 3.1 for V3D).

  • The makeWrapper env (__EGL_VENDOR_LIBRARY_DIRS, GBM_BACKENDS_PATH, LIBGL_DRIVERS_PATH, EGL_PLATFORM=surfaceless) and the video/render groups for /dev/dri/renderD128.

  • The offline shader toolchain (compiler/translate_gles.py, check_gles2.py): glslang → SPIR-V → spirv-cross --es --version 100, and a host check that compiles every shader under a real Mesa ES2 surfaceless context in CI. We validate the same way (this PR: glslang + spirv-val).

  • Boards via sbc-deploy’s sbc_board (raspberry-pi-5/4/3/02); splanc’s pi/provisioning has only Pi 5 + Pi 3 targets today, so add raspberry-pi-4 and raspberry-pi-02 (Zero 2 W).

Avoid: toxc-service.nix’s llvmpipe default; relying on llvmpipe as a fallback (use softpipe if ever needed — no LLVM); leaving -Dllvm on auto; full-frame CPU readback / dumb-buffer copies; assuming float render targets on vc4 (td-deploy never tested them — a real gap for data-in-texture effects).

Blocker to note: pi/player_rs is a static-musl binary and cannot dlopen glibc Mesa. The GPU tier needs either a glibc dynamic player build (td-deploy’s runtime_rs/cross link pattern: nixpkgs cross clang + autoPatchelf) or a separate glibc GPU helper process the musl player talks to. The helper is the lower-risk first step.

P4 shortlist (ranked)¶

  1. PIE SIMD tier for fx_vm — the only thing that speeds the kernel. Lower (via the AOT path, extended) to SoA batches of 8×i16 / 4×i32 LEDs with hardware loops, split across both cores. esp-dsp shows ~16× on int16 MAC-heavy loops; expect ~4–6× from clock+dual-core over the C6 and a further 4–10×/core from SIMD on fixed-point effects. The P4 analogue of this doc’s GPU tier.

  2. PARLIO 16-bit + BitScrambler WS2812 output — 16 strips at ~1–2% CPU; BitScrambler does the bit-transpose/expand in DMA. Needs die v3.x for the length-changing program; the 8-instruction limit is the first prototype gate.

  3. PSRAM→L2MEM tiled streaming (AXI GDMA / async memcpy) — keeps the PIE tier from going memory-bound on texture/buffer-heavy effects; double-buffered tiles, cache-line aligned.

  4. JPEG HW decode + PPA SRM — the texture/video pipeline: JPEG/MJPEG decoded and PPA-resized/converted at ~zero CPU. Replaces the refused SampleTex/video path on P4.

  5. PPA Blend for deck crossfade / layer compositing at texture scale — small-to-moderate; per-LED crossfade stays in PIE.

  6. Camera (CSI+ISP) + LP-core IMU poller — new features (camera-reactive effects, AE/AWB/histogram as uniforms), not speed.

Not worth chasing: ISP-as-colour-engine (RAW-only), H.264 encode, DSI for LEDs, RMT beyond 4 strips.

10. Prototype (//fx_gpu, this PR)¶

Host-only crate (not linked into firmware or the player). Pipeline: .fxb → lower (macro IR) → legalize (primitives for a profile) → eval (host model of the GPU result) or emit_glsl (ES 1.00 / 3.10 → SPIR-V via glslang).

  • Lowering coverage: 132 / 197 corpus shade() kernels lower to the pure per-LED subset (arithmetic, trig, colour, fixed-point, if/else, locals, memo-recompute). Refused (→ stay on VM): buffers/textures 27, unimplemented fixed vec/transcendental ops 26, dynamic-index 6, loops 3, user-fn 1, inc-local 1, driver 1.

  • Conformance (eval vs real fx_vm, 64 LEDs × 6 frames): 125/132 (95%) within 2/255; integer hash bit-exact (0); 7 over-tolerance are all class-3 transcendental-stress cases (§3).

  • Codegen validated externally: all 132 ES 3.10 compute shaders compile to valid SPIR-V (glslang -G + spirv-val); the 92 float-only effects also compile as valid GLSL ES 1.00 fragment shaders. The 40 int-needing effects are GLES 3.1 / SPIR-V only → the Pi-3-vs-Pi-4/5 tiering line, measured.

  • CI test //fx_gpu:fx_gpu_conform_test: inline effects (gradient, trig, hsv/palette, hash, if/else) lowered + compared to fx_vm within tolerance, plus refusal checks (loops and integer-on-GLES2 must fall back).

  • Run the corpus sweep: bazel run //fx_gpu:fxgpu_conform -- --profile exact --emit /tmp/shaders $(find … -name '*.fx').

  • GLES2 for vc4 = kernel in the vertex shader (Target::Es100Vertex). One GL_POINTS vertex per LED into a LEDs-per-channel × channels RGBA8 target (row = channel = one FPGA output’s address range), so 20×1024 is 1024×20 and needs no tiling under vc4’s 2048 limit. The vertex stage guarantees highp, and per-LED inputs ride as float attributes (vc4 has no float textures). Output is quantized like the VM epilogue (floor(clamp01(x)·255)) and written as q/255, so the RGBA8 store yields exactly q. (An early draft wrote (q+0.5)/255, which sits on the rounding tie, off by one.)

  • hsv2rgb on GLES2: the sextant pick uses float floor compares instead of f2i. That is exact for h6 ∈ [0,6] (NaN → 0 as in the VM), and it moved hsv-based effects (e.g. cylinder) onto the GLES2 tier.

  • Host GLES2 run (llvmpipe, harness check only): the relocated payload renders under env -i. solid_fill/imu_tilt match the VM goldens exactly; plasma/cylinder (native sin vs the VM’s LUT sine) are within 1/255 on 1–14% of LEDs. The VM bench reproduces its goldens with 0 errors.

Pi 3 measurement (step 2): done, run 1¶

fx_gpu/pi3bench builds a self-contained aarch64 payload, 37 MB. It contains:

  • an LLVM-free lean Mesa (vc4+v3d), relocated, plus the glibc loader;

  • gles2bench: surfaceless EGL, render and readback timed separately, readback formats compared, a pipelined loop, and a byte-exact check against VM goldens;

  • a static fxvm_bench VM baseline, now with --threads;

  • 8 kernels × 7 layouts, 1×500 … 20×1024.

The operator ran it on pi-ledmapper-2 through an SSH tunnel over the reservation (Reservation.forward(addr, 22); the rig container has no tar). The agent never handled the Pi key. Results are in §5: 100 JSON lines, all ok, VC4 renderer, GPU error ≤ 2/255, VM bit-exact. Open: the 4-thread VM run (--vm-threads 1,4) and the SPI-tap capture on pi-ledmapper-1 (#369 image).

11. Staged plan¶

  1. (this PR) Host IR + lowering + legalize + GLSL/SPIR-V emit + conformance harness. Design + numerics policy + P4 survey + prior art.

  2. Pi 3 GLES2 microbenchmark (HITL/Pi): done (§5). 20×1024 in 3.2–3.5 ms for every lowered kernel, ≤ 2/255. Follow-ups: the 4-thread VM run and the SPI-tap capture. 2b. Multi-thread the VM in the player (all effects, no Mesa): ~3.5× on a Pi 3 (est.). This is the cheapest MAX-scale win and comes before the GPU tier.

  3. Pi 4/5 compute path: naga SPIR-V, V3D compute over an SSBO, highp, class-1 exact; golden tolerance tests per tier.

  4. Player integration: glibc GPU helper process (musl player stays), a load-time per-effect probe (lower → tolerance-check → cache the verdict), readback → FpgaCodec → SPI; keep the VM fallback.

  5. Image: lean Mesa overlay (§8) into pi/provisioning, add Pi 4 / Zero 2 W board targets; measure closure growth. Also a pinned Pi 3 core_freq (§4). spidev.bufsiz=65536 arrives with #369. 5b. 20-channel FPGA: #370’s internal-only variant → pin map → a flashable 20-port target; PREFILL + “start on CS-end”; logic-analyzer validation on 4 channels.

  6. GPU-native textures/decks (SampleTex/blending) and shader-emulated LUT sine for class-3 exactness, if measured need.

  7. (parallel track) P4: PIE SIMD tier (shortlist #1) via the AOT path; PARLIO+BitScrambler output; JPEG/PPA texture pipeline.

12. Decisions the user needs to make¶

  1. Numerics tolerance per tier (§3): accept ≤ 2/255 (Pi 4/5 highp), ≤ 6/255 (Pi 3 mediump) as the golden-test bound? And for class-3 transcendental-heavy effects: ship the VM’s LUT sine in-shader (makes the common case exact, ~1 KB) or keep those effects on the VM?

  2. Pi 3 GLES2: recommendation: ship it, as the MAX-scale tier, after a multi-threaded VM. Data from §5:

    • It works on the stock image. vc4 KMS is already on; it needs only the lean Mesa (~40–60 MB) and a glibc GPU helper beside the static-musl player.

    • It is fast and flat: 3.2–3.5 ms per frame at 20×1024 for every lowered effect, against a single-core VM at 6.8–108 ms. That is 2.1–14.8× on the float effects.

    • It is accurate: ≤ 2/255, bit-exact for float-only effects.

    • At today’s 4×550 the VM already fits (≤ 5.6 ms for float effects, 11.6 for noise, under a 16.5 ms wire), so the GPU is not needed below ~8×1024.

    • At 20×1024 a single-core VM misses the 32.6 fps wire ceiling for every non-trivial effect. A 4-core VM (est.) fits but pegs the CPU. The GPU fits with ≥ 89% of the frame to spare and leaves the CPU free.

    • It can’t run the 32 hash effects; those stay on the (multi-threaded) VM, or move to Pi 4/5.

    Order: (1) a multi-threaded VM, for all effects at all scales; (2) the Pi 3 GLES2 tier for float-only effects at ≥ 8×1024; (3) Pi 4/5 compute, which adds the hash effects.

    Skip Pi 3 GLES2 only if MAX on a Pi 3 will never exceed ~4×1024. In that case the VM suffices and Pi 4/5 compute is the better investment.

  3. Readback vs direct DPI scan-out (§4): start with readback (recommended)? DPI is a later optimisation that costs GPIO pins and a frame-sync redesign.

  4. P4 priority (§9): is the PIE SIMD tier (shortlist #1) the P4 track to fund first, built on the AOT path, with PARLIO+BitScrambler output second?

  5. Pi 3 core_freq pin (§4): fix the VideoCore core clock so the SPI clock can’t drop below the 20-channel drain under frequency scaling? This is a small config.txt change. (spidev.bufsiz is already handled by #369.)

  6. 20-channel pin map (#370): pick the 12 extra Tang Nano 9K header pins. And should PREFILL go to 64, with the one-LUT “start on CS-end” fix, to tolerate 600 µs Pi-side pauses at frame start?
