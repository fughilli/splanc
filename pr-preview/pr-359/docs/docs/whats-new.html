What’s new¶

Notable changes, newest first. Each entry links the PRs and the doc that covers it in depth. The full history is in the git log and WORKLOG.md.

October 2026¶

1024 LEDs on each channel¶

  • The C6 player now drives up to 1024 LEDs per channel, 2048 in all (was 512 in total). Set each channel’s count on the Hardware screen. The device refuses a channel past 1024. The board reports the per-channel cap (hardware_config_state.board.max_leds_per_channel), and the app’s count field uses it.

  • LED memory is sized for the strip you configure, at boot. A board pays for its own LEDs, not the cap. A 256 + 256 fixture now has more free heap than before: 77 KB at the minimum, up from 67 KB. Raising the total past what the device booted with saves the counts and restarts it into the bigger size (reboot_required on the reply; the app says so and reconnects). The full 1024 + 1024 leaves ~29 KB at the minimum, which is the max-config cost. A total the board’s heap can’t hold is refused.

  • Long strips run slower instead of stopping. A WS2812 LED takes 28.8 µs to clock out, and the two channels go out in parallel, so the longest channel caps the frame rate: 60 fps at 512 LEDs, 40 at 768, 30 at 1024. The autoscaler never targets a rate the wire can’t carry, and fps_state.max_fps reports that ceiling. Shading 2048 LEDs takes about 50 ms even for a simple effect, so the full cap runs at about 20 fps. The abort floor now scales with the strip: 25 fps up to 512 LEDs, then 10 fps at 1024 and 5 fps at 2048. A heavy effect on a big fixture now steps down rather than being parked. See EFFECTS.md → Long strips.

  • The per-LED caches were packed (50 → 31 B per LED): topology 20 → 10 B, positions stored at 16-bit-mantissa precision (0.08 mm at 5 m), and the multi-fixture room position computed per frame instead of cached. Details: ram-budget.md → LED capacity.

  • Effects’ per-LED buffer arrays are now sized for the strip you have, not the cap. A wide buffer on 2048 LEDs can outgrow the 24 KB effect arena; declare it : fixed8.

Show Mode: browse effects with a knob; Midi Fighter Twister setup from Splanc¶

  • The effects list scrolls on its own. In Show Mode the list is a nested scroll area: swiping, the wheel or the keyboard (↑/↓, Page Up/Down, Home/End, Enter, A/B) moves it without moving the page, and the highlight stays in view.

  • Browse with an encoder, load with its push. Each deck gets a MIDI-mappable browse encoder and load button. Load either cues the highlighted effect onto the deck or takes it (loads and crossfades to that deck); pick which in the MIDI map.

  • Relative encoders scroll forever. Mappings store an encoder mode: absolute (default), binary offset (3F/41, the Twister’s “ENC 3FH/41H”), two’s complement (7F/01) or signed bit. MIDI learn detects the mode from the values the knob sends. A faster turn moves further.

  • Set up Midi Fighter Twister (MIDI map, or Settings ▸ MIDI) switches the encoders you pick to relative mode over SysEx. It reads the Twister’s settings, shows what will change, writes only those fields, reads them back to check, and maps the encoders. It needs Chrome or Edge on a computer or Android; iOS has no Web MIDI. Not yet tested on a real Twister.

  • Guide: Show Mode & the mixing deck.

Copy a fixture’s map onto a new phone¶

  • The Maps tab shows the map on the connected device. A card at the top shows its LED count, mapped vs interpolated LEDs, and whether this phone already has it. On a fresh install, Save to this phone copies the map into the library, and Preview opens it without saving. Only a small header is read on each visit. A large map is downloaded when you save or preview it.

  • Calibrate IMU without mapping again. The card and the device’s detail sheet offer Calibrate IMU when the device’s motion sensor is running. If the map isn’t on this phone yet, it is copied first.

  • Supplement works on every map. A map copied from a device or imported has positions but no raw capture data. A supplemental scan now aligns to those stored positions and averages with them, using a cautious accuracy of ¼ LED pitch for the stored positions. Before, the button was hidden for these maps. Maps that kept their capture data still get the joint re-solve. The debug Bundle tile is now greyed out with the reason, not hidden.

  • Not yet through Live via bridge: the bridge doesn’t forward the stored map, so connect to the fixture directly to copy it.

A quickstart guide¶

  • New: the Splanc quickstart. Wiring, flashing, Wi-Fi, mapping, effects and AI agents, one short section each, from a bare ESP32-C6 to animated lights.

The motion sensor knows which way the map is¶

  • Mapping now calibrates the IMU’s tilt for free: the map is gravity-levelled and the fixture stands still while it’s captured, so the sensor’s settled “up” is pinned to the map’s +Y as soon as the map is stored; effects tilt the right way at once. Heading needs a second, re-oriented pose (the guided “Calibrate IMU” screen is next); the solver and device side are in (sensor-core.md §7).

  • Fixtures remember how they were mapped: diffuse mode, LED stride, code timing and brightness are stored on the device with the map, and a later supplemental or calibration capture reuses them instead of re-probing.

Sensor drivers an agent can write¶

  • Any I2C sensor, no firmware release. Agents scan the player’s sensor bus (scan_i2c), write a small driver in the effect language (void poll() + exports, i2c_read* / i2c_write), and load it live (deploy_driver); every export drives the effect uniform of the same name. Supersedes PR #96; the native-vs-VM MPU-6050 A/B and when to use which: sensor-core.md §8.

Fixtures that feel motion: the sensor core¶

  • Wire an MPU-6050 and the player finds it. At boot the C6 player probes its I2C pins (SDA 6 / SCL 7, INT 21 by default) for an MPU-6050-family IMU, fuses it on the device (orientation, gravity, linear acceleration, shake and tap), and costs nothing when none is fitted.

  • Effects react by name. Declare uniform vec3 imu_gravity, imu_quat, imu_shake, imu_tap, … and the firmware drives them every frame; without a sensor they stay ordinary knobs. Try agent/skill/examples/imu_tilt.fx.

  • Agents can read and calibrate it (read_sensors, calibrate_sensors). Design: sensor-core.md (#315).

Live VJ through your bridge: every fixture from one phone¶

  • ⋯ → Live via bridge in the app pairs with your Splanc bridge (the code on its screen, like an agent) and drives all its fixtures at once: pick fixtures or rooms, cue effects on decks A/B, crossfade, brightness, the effect’s sliders and keypoint pads. A fixture takes one connection at a time; the bridge holds them all, so phones and agents can share it.

  • From anywhere through the relay, or directly on the bridge’s network (lower latency: ~1–2 ms to the bridge instead of a relay round trip); the status pill says which.

  • Show Mode lock keeps agents (including crossfade_to) and other phones off the fixtures you’re performing on.

  • Design, numbers and free-tier costs: live-vj-relay.md.

The bridge follows players that come back on a new IP¶

  • Players are tracked by device id, not by address. Players that pick a new Wi-Fi MAC on every boot get a new IP each time. A bridge that keeps running now finds such a player again by itself, through mDNS or a LAN sweep for its manifest, and moves it to the new address. You don’t need to call add_player. If you call add_player with a known player’s new address, that player is updated, and its stale old address is dropped. A different certificate under a known id is reported as TLS CHANGED.

  • Dead sessions are noticed. Every player session has a heartbeat. A player that vanished fails the call within seconds, with the reason, instead of hanging. list_players shows each session’s state and when the player was last heard.

  • Errors name the cause. Tool calls the relay or bridge can’t complete come back as tool errors with the reason (bridge disconnected, offline, timed out, ECONNREFUSED, a stale PERMANENT ARP entry on the bridge…). Before, MCP clients showed only “MCP tool call failed”.

Agents crossfade between effects, and look at your fixtures in 3D¶

  • crossfade_to fades from the running effect to a new one (its source, or an effects-library entry by library_id) instead of cutting. The bridge loads the new effect onto the player’s idle FX deck (the second deck Show Mode uses), then glides the crossfade over the seconds you ask for, with a choice of curve (ease by default) and RGB or HSV blending. With several players or a room, every player fades on one clock, and the effects share one time base, so the room changes together.

  • Rollback keeps working. The effect you faded away from stays loaded on its deck, even one the app put there, so rollback_effect fades straight back to it (call it again to swap forward). list_decks shows what is on decks A and B, where the crossfade sits, and which deck is live. Uniform and keypoint tools follow the live deck.

  • Deck B is runtime-only: if a crossfade ends on it, a reboot brings back deck A’s effect. deploy_effect still makes an effect permanent. Both effects render while the fade runs, and they share the 24 KB buffer arena, so a too-large pair is refused with that explanation.

  • plot_fixture returns a PNG of a fixture’s LED map from the front, side, top and an isometric view. It shows metres with +Y up, axes, the bounding box, the wiring order, LED index hints and a scale bar. Mapped LEDs are dots and interpolated ones are rings. You can colour the LEDs by index, solve confidence, segment, channel or one frame of an effect. A room plots every fixture at its pose in one scene. The numbers (mapped vs interpolated, bounds) come with it. The image is drawn in plain TypeScript, so it works on the Pi bridge, and stays small enough for the cloud relay. The CLI has crossfade-to, list-decks and plot-fixture --out <dir>.

An effects library that grows with every scene¶

  • Agents look before they write. Each installation now keeps a private library of effects that worked before: what each looks like, its tags and its knobs. Asked for a new scene or mood, the agent searches it first (search_effects), deploys a match in one call (deploy_effect {library_id}) or copies and adapts a close one (duplicate_effect), and only writes a new effect when nothing fits.

  • It fills itself. Every successful deploy is kept, with its description, tags and measured frame cost; the agent is asked to describe any it deployed without one. New libraries start with Splanc’s example effects.

  • Served by the cloud relay, so it’s fast and still browsable while the bridge is off. Without the relay (a local agent over stdio or the CLI) the same tools keep it in a file in the agent’s state dir. Nothing is shared between users. Design: cloud-relay.md § Effects library; how to use it: cloud-agent.md.

A good live preview no longer ends in an empty map¶

Some captures showed the fixture correctly in the live preview, then the final solve came back degenerate. The cause: the final solve started over from scratch, and on gentle or decode-swapped captures its first scale estimate can come out negative. That flips the whole scene behind the camera, and the optimizer can’t recover. Each preview solve rolled its own sign, so the preview could look right while the final didn’t. Analysis and fix: mapping-solve-paths.md.

  • The solver rejects an implausible starting scale and starts from an arm’s-length guess instead. The optimizer and the motion data then find the real size.

  • The final solve also starts from the best live-preview solve and keeps whichever start solves better.

  • If the final is still degenerate (it failed, has far fewer LEDs, or collapsed) while the preview wasn’t, the app keeps the preview’s map and adds a warning that says why.

Debug mode logs failed mapping runs¶

  • Turn on Settings ▸ Behavior ▸ Developer ▸ Enable Debug Settings, and every mapping run that fails, comes out degenerate, or disagrees with its preview saves a capture bundle on the phone. Keep successful runs too saves the rest as well.

  • A bundle holds everything needed to replay the run’s solves exactly: detections, motion data, capture settings, the fixture’s firmware version, the preview and final solves with their diagnostics, and the app and solver builds.

  • Export or share bundles from Settings ▸ Debugging ▸ Mapping capture bundles, as one .splanc-capture.json file. A saved map’s Bundle tile (in debug mode) rebuilds one from a map you already captured.

  • Developers replay a bundle bit-for-bit through the wasm build with bazel run //solver:replay_bundle -- FILE, or natively with per-stage traces with solver_cli --replay FILE. See the user guide.

Splanc works as a ChatGPT plugin¶

  • Add https://splanc.pages.dev/mcp in ChatGPT as a custom MCP server with OAuth, sign in with your bridge’s pairing code, and ChatGPT drives your lights. Steps: cloud-agent.md.

  • Every agent tool says what it does: read-only tools (listing, previews, compiling) run without a confirmation prompt in ChatGPT; tools that change the lights ask first, and deleting or overwriting your saved things is flagged as destructive. The server also gives agents a short “how to use Splanc” note.

  • The relay advertises offline_access, so ChatGPT keeps its sign-in, accepts ChatGPT’s client metadata document, and ignores scopes it doesn’t use (like openid) instead of failing.

Show the Wi-Fi password while you type it¶

  • An eye button at the right end of the Wi-Fi password field in the add-device sheet shows the password in cleartext, and taps back to hidden. It starts hidden, keeps the keyboard open and the cursor where it was, and picking a saved network keeps your choice. Phone keyboards no longer autocorrect or capitalize the field, and password managers leave it alone.

  • The same button is on the API key fields in AI settings and on the Splanc Bridge Flasher’s Wi-Fi password (which had a text “Show” button).

Players keep one address¶

Netstack players picked a random Wi-Fi MAC (02:0c:6a:…) every boot, so the router handed them a new IP after every reboot and the bridge kept dialling the old one. They now use the chip’s factory MAC, so the lease (and any DHCP reservation) stays put, and a re-join first clears any stale association the AP still holds. mDNS re-announces on every new lease and after a DHCP renewal; the TXT record carries the device id. HITL gate: //pi/hitl/harness:stable_identity.

Players stay on Wi-Fi across updates and power cuts¶

Netstack players kept their Wi-Fi name and password in RAM only, so every reboot (a power cut, a reset, a firmware update over USB) brought the board back unprovisioned, and it had to be put back on the network. Now the credentials are saved to NVS once the board has actually joined with them (a mistyped password is never saved), and the board rejoins on its own at boot. Re-provisioning the network a board is already on keeps the link instead of restarting the join. If the saved network wasn’t visible at boot (the router still starting after a power cut), the board restarts to rescan on a capped backoff. Design notes: firmware/player_app/wifi_creds.h; HITL gate //pi/hitl/harness:upgrade_keeps_wifi.

  • One last re-provision. A board running a release before this fix has no saved credentials to keep, so the update that installs this firmware still needs one provision; every update after that keeps them.

  • Factory reset (a full flash erase) still clears them.

Every player has its own TLS certificate¶

Netstack firmware used to serve one shared certificate, and its private key was in the open-source tree, so any device could be impersonated. Now each player generates its own EC P-256 key and self-signed certificate on first boot. It keeps them in littlefs (power-loss-safe) for life: there’s no IP in the cert, so DHCP changes don’t rotate it. Only a factory reset (flash erase) makes a new one. Design, the vendor build’s re-issue races it avoids, and the measured cost: per-device-cert.md.

  • Never serves without a cert. Generation runs in setup() before WiFi comes up, and :443 opens only once the identity is installed. Until then mDNS advertises tls=generating and the new get_tls_info (over BLE too) reports generating.

  • Trust on first use.

    • The agent bridge pins each player’s certificate by id in hub.json. A changed certificate is refused (tls: CHANGED) until trust_player.

    • The app remembers each device’s certificate and warns in the device sheet, with an “I reset it — trust the new certificate” action.

  • Upgrades are quiet. A device moving off the old shared certificate is re-pinned without a warning.

  • The manifest’s tls block now carries state and persisted.

Export a map to TouchDesigner or Chromatik¶

  • Export map in the mapping workspace downloads the fixture’s LED positions, one entry per LED in output order. Two formats:

    • a CSV laid out as a TouchDesigner Points DAT (index,P(0),P(1),P(2),mapped,confidence,channel,channel_index,segment,arclength, metres, +Y up). Load it in a Table DAT and feed a DAT to SOP, no editing.

    • a Chromatik .lxf fixture (points components per channel, with a Scale parameter that defaults to centimetres).

    Unmapped LEDs keep their index with mapped=0 and an interpolated position. A Z-up option covers Blender-style tools. On iOS the file goes through the share sheet (“Save to Files”). Agents get the same files from the bridge’s export_map tool / splanc-agent export-map. See the user guide.

Splanc bridge SD image + Splanc Bridge Flasher (no terminal)¶

  • Splanc Bridge Flasher (macOS, Windows, Linux): a desktop app that writes a Splanc bridge microSD card. Pick the Pi model, type the Wi-Fi name and password (plus the Wi-Fi country and, optionally, a name for the Pi), pick the card. It downloads the newest image, checks its sha256, writes the card, reads it back to check every byte, and puts the Wi-Fi settings on it. Boot the Pi and the pairing code is on its HDMI screen or OLED HAT. Only removable disks are ever offered. Guide: Set up a Splanc bridge on a Raspberry Pi.

  • Splanc bridge SD image for the Pi 5, Pi 4, Pi 3 and Zero 2 W: a small NixOS system that runs the bridge and the screens from power-on, with no login. It applies the flasher’s settings at boot (and moves the Wi-Fi password off the card), and updates the Splanc agent by itself (sha256-checked, from splanc.io/agent/latest.json).

  • Own release track: pi-bridge-v* releases carry the images (splanc-bridge-<board>-<ver>.img.zst + .sha256) and the flasher installers, built by .github/workflows/pi-bridge-image.yml, separate from firmware-v* and app-v*. Details: pi/bridge/README.md.

  • The curl … | sudo sh installer below stays, for Raspberry Pi OS installs you manage yourself.

A Raspberry Pi as a Splanc bridge¶

  • One-command Pi bridge appliance: flash Raspberry Pi OS Lite with Imager (Wi-Fi and SSH preset), boot, then run curl -fsSL https://splanc.io/bridge/install.sh | sudo sh. The Pi runs the Splanc cloud bridge headless and starts it on every boot. It updates itself daily, checking each release’s sha256. Guide: Set up a Splanc bridge on a Raspberry Pi.

  • Status screens: a full-screen HDMI page (no desktop needed) shows the pairing code, a QR code, the fixtures, the clients and the network. A Waveshare 1.3” OLED HAT shows pages of the same information. Its keys work as follows: KEY1 gets a new code, KEY2 identifies fixtures, and holding KEY3 then confirming revokes all clients. The joystick pages through the screens.

  • Built in: the installer and display service live in pi/bridge/ and ship inside the agent bundle (pi-bridge/, plus site/bridge/install.sh). Details: pi/bridge/README.md.

AI agents can drive Splanc (“Use splanc.io to set the mood of the room”)¶

  • Agent bridge + bundle (#274): agent/ is an MCP server (stdio) and a one-shot CLI over the same tools. It is shipped as splanc-agent-<ver>.tgz on every firmware-v* release, along with the matching compiler and simulator wasm, the protocol schema and an agent skill. See agent/README.md.

  • Multi-fixture hub (#278): one bridge drives every player on the LAN. It covers:

    • mDNS browsing, remembered players and a bounded /24 manifest sweep;

    • one socket per player, with parallel fan-out and per-player results;

    • rooms, fixture poses and a shared time base;

    • per-firmware toolchains fetched from each player’s own bundle.

    Design: agent-multi-fixture.md.

  • Device discovery (#276): GET /.well-known/splanc.json (identity, firmware, protocol features, .fxb format, TLS cert pin, agent bundle), an mDNS _splanc._tcp responder on the netstack, plus these protocol additions:

    • Welcome.features and fxb_format;

    • set_uniforms.commit (apply a uniform live without persisting it);

    • list_effects;

    • a complete get_effect_uniforms.

  • Uniform docs: doc, min, max and unit are now in the effect manifest (from the uniform’s source comment).

  • Room frame and shared time (#280): set_fixture_pose / set_time_base, the led.room / room.min / room.max effect builtins, and a HITL test that measures inter-fixture skew against a 20 ms target. See EFFECTS.md.

  • splanc.io entry point: splanc.io serves /AGENTS.md, /llms.txt, /.well-known/mcp/server.json and the newest bundle at /agent/splanc-agent.tgz. The one-liners are:

    claude mcp add splanc -- npx -y https://splanc.io/agent/splanc-agent.tgz
npx -y https://splanc.io/agent/splanc-agent.tgz list-players

  • Keypoint tools for agents (#286): list_keypoints, save_keypoint, recall_keypoint, blend_keypoints and delete_keypoint, plus each player’s keypoints in splanc://effect/active. The skill maps “save the look as a keypoint” and “morph between moods” onto them. They are gated on the keypoints feature (see below).

Saved looks: uniform keypoints, two decks and a crossfade¶

Supersedes #82 (FUG-110). Design: uniform-keypoints.md.

  • Keypoints (#285): a keypoint is a named set of uniform values for one effect, a known-good position in its parameter space (“dawn”, “storm”). They are stored on the device in littlefs (power-loss-safe, at most 16 per effect), so the app, Show Mode and agents all see the same set. Values are stored by uniform name, and a keypoint saved against an older build of the effect is flagged stale.

  • Morphing on the device: recall a keypoint over N seconds, or blend up to four with weights. The device eases the uniforms itself, once per frame, using each uniform’s manifest rule (sliders interpolate and clamp to min/max, colours blend in linear RGB or HSV, toggles and dropdowns take the nearest source). A live blend never writes flash; saving the blended look is explicit.

  • Two decks + crossfade: the player runs deck A and deck B at once and crossfades their per-LED output (linear RGB or HSV). Deck B shares one memory region with the video-texture delta buffer, so loading deck B ends a video stream on that player. Deck B is interpreted (no JIT) and is not restored after a reboot.

  • In the app: the effect editor and each Show Mode deck (/show, from the Effects ⋯ menu) carry a keypoint strip: tap a pad to recall it, “＋ Save” to store the live uniforms, a morph fader to slide between two pads, long-press or right-click to delete. Show Mode’s MIDI layer can map the crossfade, blend mode, per-deck play/pause and cue, each deck’s keypoint morph fader, and next / previous / save keypoint.

  • Wire: set_crossfade = 39 and the keypoint arms 40–44 (replies keypoint_list = 22, keypoint = 23), a deck field on the effect messages, and the decks, crossfade and keypoints features. The full table is in uniform-keypoints.md.

  • Cost: +6.5 KB of static RAM, and the per-LED shade entry pinned back in IRAM (.iram0.text 97,512 → 99,704 B). With both decks and a wss session the fx_keypoints HITL run measured a 72.7 KB minimum free heap. The sweep16 fx_bench golden was re-baselined (42,589 → 50,259 cycles) on evidence that the remaining gap is flash-cache layout, not added work; the evidence is on #285.

Effect authoring: measure on the fixture, not just in the model¶

  • measure_on_device (#292): the editor’s and Acid Mode’s AI chat can run the current script on the connected fixture with full perf reporting and read a few seconds of the device’s perf stream (mean / p95 / max frame time, the update / shade / show split, budget fraction), next to the offline estimate_performance. The agent iterates offline and confirms on the device before calling a performance goal met; when they disagree it optimizes against the measurement. The tool is offered only while a fixture with the perf feature is connected, and never in the website demo.

  • The hub gained the same pair: estimate_effect (offline, touches nothing) and measure_effect (windowed on-device stream, now in milliseconds).

The C6 player’s memory, from 1.6 KiB to ~87 KiB of worst-case headroom¶

Measured on the ram_audit HITL worst case (BLE provisioning → first wss handshake → 512-LED map and texture effect → loaded handshakes). Detail in ram-budget.md.

  • Zero-copy envelopes (#262): the board-capabilities reply is spliced in encoded form, so the firmware ServerMessage shrank from 4,104 B to 656 B. Requests dispatch in place, and task stacks are sized from a static bound (loopTask 48 → 20 KiB).

  • pbview (#265): zero-copy no_std protobuf views (oss/pbview), so the firmware decodes every request straight from the RX frame.

  • Vendor Wi-Fi residue freed and dead SDK code moved out of IRAM (#266):

    • ~20 KB of vendor heap freed (no lwIP task, the event loop deleted after the scan, no NVS mirror);

    • an @embedded sections.ld override moves cold vendor code to flash (.iram0.text 114,910 → 97,512 B).

  • Zero-copy TX (#267): each outbound frame is built once, in place (loopTask 20 → 14 KiB).

  • Native pulse/flood playback removed: every show is an FX-engine effect. set_playback accepts only "off", and the render stack went from 8 to 5 KiB. firmware/pulse remains for the web simulator only.

  • Static stack-bound CI gate (#270): //tools/stack_bound over the shipped ELF’s call graph fails the build when a task’s bound, plus margin, outgrows its stack.

  • Post-boot heap census (#271): every allocation after setup() is attributed to its call site and read over JTAG. See heap-census.md.

  • TLS region (#272): mbedTLS allocates from its own fixed slots and private region, off the shared heap.

  • Unbuffered littlefs (#273): removes a 4 KB stdio buffer per file open.

  • Exact-size topology decode (#291): a topology upload is decoded in two passes (count, then fill exactly), with every polyline in one shared vertex array, and the topology arena grew from 8 to 12 KB. A scan needs 16·J + 24·S + 12·V bytes for J junctions, S segments and V vertices: a 462-LED scan with 27 / 51 / 206 now takes 4,128 B (it overflowed 8 KB before), leaving room for ~880 vertices at that junction and segment count. Beyond that the upload fails with map_too_large.

  • Memory regions and the mode model (#263, #269): firmware/region (pools, slabs, mode unions) and firmware/sysmode, a reachability-checked model of the device’s memory modes, which the firmware now tracks (log-only). See memory-regions.md.

  • Kani under Bazel (#264): the region proofs run as hermetic rust_kani_test targets. See kani-bazel.md.

  • PR-38: BLE and wss coexist. Making the radios mutually exclusive is not an allowed memory lever.

Tooling, HITL and releases¶

  • The netstack answers ping (#302): ICMP echo requests to the player’s own IP get a reply, rate-limited to 10/s (burst 5) so a flood can’t starve the LEDs or TLS. Broadcast/multicast pings and fragments are ignored; up to 1472 data bytes (one 1500-byte MTU packet) are echoed.

  • ram_audit --hang (#270): catches a hard hang over JTAG before the watchdog erases it. RAM dumps are armed only after provisioning, because a ~46 s halt during the Wi-Fi join resets the board.

  • Android flashing (#268): the USB-JTAG connect resets and reopens the port, and the C6 flash-ID probe is fixed.

  • splanc.io/app follows app releases (#277): every app-v* tag now publishes splanc-webapp-<ver>.tar.gz, and splanc.io stages the newest one.

  • Fleet dashboards (#279): the Android bench (amd-rig) and the iPhone bench (mac-mini) push metrics to Grafana, and the dashboard sync warns loudly instead of skipping silently.

  • Release stamps the agent bundle (#293): release.yaml passes the bundle’s URL and sha256 into the firmware build, so a released device’s /.well-known/splanc.json names its bundle with a hash.

  • ffi_test is one #[test] again (#294): the FFI state is process-global, and a second test raced it on the harness’s threads.

  • Docs: the Splanc manifesto, on why the system is built the way it is.
