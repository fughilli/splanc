Host player: Splanc on a Mac, driving WLED / DDP / Art-Net controllers¶

//pi/player_rs:player_host runs the Splanc player on a desktop host (macOS or Linux) and drives LEDs through network pixel controllers instead of a Pi’s SPI bus. The controllers are treated as dumb pixel sinks. A WLED board in realtime mode is the main target. Everything Splanc does is computed on the host: the mapping patterns, LED counting and effect frames.

To the app it is one more fixture. You add it by address, map it with the phone camera, and push effects to it. The session core is the same one the ESP32 and the Pi players run. Effects run on the device’s fx_vm, the same VM the browser preview uses, so a fixture shows what the preview shows.

 phone app ──wss──▶ player_host (Mac) ──UDP (DDP / Art-Net)──▶ WLED board ──▶ LEDs
                    session core + fx_vm

Build and run¶

The repo’s normal Bazel setup applies: Bazelisk, plus Nix for the toolchains, which is what the test-macos CI job installs. The player needs nothing Linux-only.

bazel build //pi/player_rs:player_host
bazel-bin/pi/player_rs/player_host --output ddp://wled-desk.local --leds 300 --name "Desk"

bazel run //pi/player_rs:player_host -- --output … --leds … works too.

Flag

Meaning

--output SPEC

An output driver. Repeat it to split one strip across several controllers, in order. Default null.

--leds N

The strip length. Defaults to the outputs’ #N counts added together.

--fps F

The output frame rate. Default 40.

--name NAME

The device name the app shows. Default “Splanc Host”.

--serve-port P

The WSS port. Default 8443. Use a different port for each process.

--state-dir DIR

Where the map and effect are saved ("" keeps them in memory only). Default ~/Library/Application Support/Splanc/player_host/<port> on macOS, ~/.local/state/splanc/player_host/<port> on Linux.

--start N

Show an N-LED mapping pattern at startup without the app, to check wiring.

Output specs (pi/player_rs/src/output.rs)¶

Spec

Wire

ddp://host[:port]

DDP to port 4048: 480 RGB pixels per packet, PUSH set on the last one. WLED takes it with no configuration.

artnet://host[:port][?universe=U][&sync=1]

Art-Net ArtDmx to port 6454: 170 RGB pixels per universe, starting at universe U (a 15-bit port address). sync=1 sends an ArtSync after each frame. Broadcast destinations work.

null

Drops every frame, for timing the render loop with nothing attached.

Add #N to give one output N pixels, for example --output ddp://a.local#300 --output ddp://b.local#150. Outputs without a count share the pixels left over. Unused pixels at the end of an output are sent dark.

Colour order: the player sends RGB. Set each strip’s real colour order (GRB and so on) in WLED. If you set a colour order in the app’s hardware settings, it is applied on top of that.

WLED setup¶

  1. Prefer wired Ethernet for the board. Mapping and effects stream on every frame, and Wi-Fi adds jitter.

  2. In WLED, open Config → LED Preferences and set the LED count, GPIO and colour order for the strip.

  3. Open Config → Sync Interfaces → Realtime and turn on Receive UDP realtime. DDP needs nothing else. For Art-Net, set Type to Art-Net, set Start universe to the same value as ?universe=, and use the multi-RGB DMX mode.

  4. The player keeps sending frames (black when idle), so WLED stays in realtime mode while the player runs. It falls back to its own effects after its realtime timeout once the player stops. If WLED also dims realtime data, check its realtime brightness setting (Force max brightness) so the app’s brightness is the only one that applies.

Using it from the app¶

  1. Start player_host. It logs add it in the app at wss://<this host>:8443.

  2. In the app, choose Add device → Enter address and enter wss://<mac-hostname-or-ip>:8443. The player uses a self-signed certificate, like the devices do. The first time, open https://<host>:8443 in the same browser and accept the warning. The page itself then shows an error, which is expected.

  3. Map it the usual way: set the LED count, run the capture with the phone camera, and solve. The player shows the mapping patterns over DDP or Art-Net and reports back which frame it showed, as the devices do. Effects need the solved map on the player, so make sure the app uploads it.

  4. Push effects from the Effects tab. The map and the active effect are saved to the state directory and come back after a restart.

What is supported¶

The effects layer is pi/player_rs/src/fx.rs. These are served:

  • Mapping and LED counting (the shared session core).

  • submit_map, including sparse maps. Unmapped LEDs get positions interpolated from their neighbours, as on the device.

  • upload_chunk reassembly. The app splits any frame over 4 KB this way.

  • On one deck: submit_effect, set_effect, set_uniforms (with control_ack), get_effect_uniforms and list_effects.

  • Output brightness.

Not served yet. The welcome’s feature list leaves these out, so the app doesn’t offer them:

  • Deck B and crossfades.

  • Keypoints.

  • Textures and video input.

  • Topology (led.seg / led.s / led.branch read as “none”).

  • The stored-map dump back to the phone (stored_map).

  • Per-fixture room poses (the room box is the map’s own box).

  • Perf reports, the FX debugger and OSC.

Uniform values are not saved. After a restart the effect starts from its manifest defaults.

Testing¶

  • Unit tests: bazel test //pi/player_rs:player_rs_test. These cover the DDP and Art-Net packet formats, output specs and pixel layout, and the effects layer end to end with a real compiled shader (map, chunked upload, uniforms, uniforms manifest, restore).

  • Live smoke test, no hardware needed: pi/player_rs/tools/smoke_host.py (usage in its header). It runs the real binary, connects over real WSS and checks the DDP pixels that come out.

Handoff: where this stands (2026-11-11)¶

This was written and tested in the Linux dev container. It has not yet been run on a Mac, against a real WLED board, or with the phone app. Next steps, in order:

  1. Build on the Mac. Run bazel build //pi/player_rs:player_host, then bazel test //pi/player_rs:player_rs_test and the smoke test. The test-macos CI job already compiles //pi/player_rs/... on macOS, so the first build is expected to work. If it fails, check Xcode Command Line Tools (the linker) and the Nix install first.

  2. One WLED board. Run player_host --output ddp://<board> --leds <n> --start <n>. The strip should show the mapping pattern. Then drop --start, add the player in the app and run a real mapping capture. Check that the solve looks right and that the pattern decodes cleanly over the network. Network latency is the untested part.

  3. Effects. Push an effect from the library and compare it with the preview.

  4. Several boards. Either run one player_host per board on different --serve-ports (each is its own fixture in the app), or split one fixture across boards with #N counts.

  5. Open choices. Whether to add deck B and crossfades (port them from firmware/player_app/ffi.rs), sACN/E1.31 output, mDNS advertising so the app finds the player without typing an address, and a launchd plist so it starts at login.
