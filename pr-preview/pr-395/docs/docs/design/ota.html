Firmware updates over the air (split loader + app)¶

Status: implemented (PR “OTA: split loader + app”). HITL results at the end.

A Splanc C6 player updates over Wi-Fi from the web app, the agent (update_firmware) or the bridge. A small loader in the factory slot owns updates and recovery. The app (the player) never writes an image itself. A new app has to prove itself healthy before it is kept, and if it can’t, the device falls back to the loader, which stays on the network to take another image. Existing devices need one USB flash to get the new layout, and it keeps their Wi-Fi credentials, TLS identity and stored map.

Constraints that set the design¶

Flash is 4 MB. All five C6 DUTs on the HITL rigs report ESP32-C6FH4 (QFN32) with Detected flash size: 4MB (esptool flash_id, 2026-10-21: c6-003f08, c6-123170, c6-2ce684, c6-117d10, c6-fa3304). The FH4 is the SuperMini’s chip, with 4 MB of in-package flash. A DevKitC-1-N8 has 8 MB, but the design has to fit the boards people actually use. The loader logs the size it reads from the chip at boot (esp_flash_get_size, [loader] boot … flash=4096K).

The loader is big because the Wi-Fi path needs the vendor Wi-Fi/PHY blobs (≈220 KB of ieee80211/pm/wpa/… text), mbedtls with TLS and x509 (≈290 KB), plus the Arduino/IDF core. Dropping the player itself (FX VM, JIT, keypoints, micropb, LED drivers) saves only ≈500 KB.

The loader has no BLE. The BLE controller and heapless host cost ≈250 KB (1,548,624 B with BLE). That space buys littlefs room for a 2048-LED map (#335: the upload peaks at ≈245 KB) and keeps app headroom.

What the loader gives up is BLE Improv provisioning while in recovery. It still has Wi-Fi:

  • the credentials the app persisted (#311);

  • the wired console’s PROV <ssid> <pass> line.

The app does BLE provisioning as before. The case that now needs USB is narrow: the app is broken, and the stored Wi-Fi network is gone.

Two OTA slots don’t fit: 2 × 2.08 MB is more than the 3 MB the legacy table gives apps. A Wi-Fi loader plus one app slot doesn’t fit in that 3 MB either (1.28 + 2.16 = 3.44 MB, and 1.55 + 2.16 with BLE). The only partition that can give room is littlefs, which the legacy table sizes at 896 KB and which holds well under 100 KB in practice: a 512-LED map is about 20 KB, plus the topology, the effect (≤ 4 KB), the TLS identity (1 KB), the colour LUT (1 KB) and keypoints. The 64 KB coredump partition is unused on the C6.

Roles and boot flow¶

The stock IDF bootloader boots app when otadata selects it, and loader (factory) otherwise. App rollback is enabled in the prebuilt bootloader (CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y): an app selected by esp_ota_set_boot_partition boots pending verify, and if it resets before it marks itself valid, the bootloader marks it aborted and boots the loader. This is the same mechanism the swarm loader uses.

loader (firmware/loader/loader_main.cpp), every boot:
  0. littlefs: mount; first boot after the USB migration -> copy the legacy fs (below)
  1. decide (firmware/ota boot.rs loader_decide, host-tested):
       resume record in NVS (a transfer in progress)      -> recovery "incomplete"
       app handed over (NVS handoff): update / stay / crash loop -> recovery
       slot has no valid image                            -> recovery "no_app"
       app aborted/invalid (rolled back):
           power-on/brownout/external reset and retry unused -> boot it once more
           otherwise                                       -> recovery "rolled_back"
       else                                                -> select the app, restart
  2. recovery: join Wi-Fi with the stored credentials (NVS "ledmapper"/ssid,pass,
     #311's keys; no BLE: a wired PROV line also works), serve wss:443 with the device's
     own TLS identity (littlefs /lfs/tls_id.bin), answer mDNS (_splanc._tcp, TXT
     mode=loader), take an image (ota_begin/ota_chunk/ota_finish).
     Reason "update" returns to the app after 5 min with no session, or 30 s after
     a refused offer.

app (firmware/player_app/ota_app.cpp):
  boot: crash-loop guard (RTC no-init counter of consecutive panic/WDT resets;
        3 -> hand over to the loader, reason crash_loop). Pending verify -> arm the
        RTC (LP) watchdog for 150 s; Arduino's verifyRollbackLater() returns true,
        so nothing is marked valid at boot.
  loop: health (boot.rs health): up >= 20 s AND render task ticking AND TLS identity
        ready AND (DHCP lease, if the loader itself had one when it booted us)
        -> esp_ota_mark_app_valid_cancel_rollback(), disarm the watchdog,
           NVS last_result="ok".
        Not healthy by 120 s -> esp_ota_mark_app_invalid_rollback_and_reboot().
        Wedged too hard to do even that -> the watchdog resets at 150 s, and the
        bootloader rolls back.
  ota_begin: check the manifest's shape, size and version order, write NVS
        handoff=update, reply STATE_REBOOTING, select the factory app, restart.

The network health check only counts when the loader was on the network when it booted the app (NVS net). An AP that is down during an update must not roll back a good image.

Keeping the IP across the handoff¶

Since #326 the netstack joins with the chip’s factory Wi-Fi MAC, and clears any stale association on rejoin. The AP’s DHCP server leases by MAC, so the IP survives every restart: the app → loader handoff, an install, and a power cut. Before every planned restart (the handoff, booting an installed app, ota_reboot, the idle return), netstack_prepare_restart() also sends the AP a Deauth (reason 3). The AP then drops the association before the same MAC comes back.

A release’s .ota package is this manifest followed by the image.

Checks:

  • The loader is the authority. It verifies the signature with mbedtls (the C6’s ECDSA-verify and SHA accelerators) against the key compiled into it (ota_key.h, generated from firmware/ota/keys/*.pub).

  • At boot the loader runs a known-answer test (ota_kat.h: a good signature must verify and a flipped bit must not). sign_test pins that file to the signer’s output.

  • Before the first erase, the loader checks the image header in chunk 0: magic, chip id 0x000D (C6), appended SHA, app descriptor.

  • After the last chunk, the loader reads the whole slot back through SHA-256 and compares it with the signed digest, then runs esp_image_verify.

  • The app checks only the manifest’s shape, size and version order. It holds no key, so test images don’t need a second app build, and a bad signature costs one round trip through the loader, which refuses it and returns to the app.

Flags: the manifest’s flags carry the signing key id (bits 8–15) and a security version (bits 16–23). Both are inside the signed bytes. Key id 0 at security version 0 is flags 0, the swarm’s default, so the 108-byte layout is unchanged.

Signing¶

The release key. The private key is the OTA_SIGNING_KEY repository secret:

  • Where it lives: Settings → Secrets and variables → Actions → Repository secrets. It is not an environment secret; the firmware job in .github/workflows/release.yaml has no environment:.

  • Format: the raw P-256 private scalar as 64 lowercase hex characters, exactly the private line that keygen prints. Not PEM, not DER.

  • Generate it with keygen, naming the key you are making (the full procedure and the other keys are under “Key names” below):

    bazel run //firmware/ota:ota_sign -- keygen --name release

    The output names the exact secret and file for that key:

    key: release (id 0)
private (store as the OTA_SIGNING_KEY repository secret, never in the repo): <64 hex chars>
public  (commit as firmware/ota/keys/release.pub): 04<128 hex chars>

    A new release key replaces a trusted one, so follow the rotation runbook below rather than overwriting release.pub.

The public half is committed as firmware/ota/keys/release.pub: the SEC1 uncompressed point as 130 hex characters, with optional # comment lines. Both ota_sign pubkey and ota_sign check-pub print that same format, and //firmware/ota:sign_test checks the committed key parses as a P-256 point in that form.

What the release workflow does:

  1. Builds the OTA bundle and the signer.

  2. Fails loudly unless ota_sign pubkey --key-env OTA_SIGNING_KEY equals ota_sign check-pub --in firmware/ota/keys/release.pub. A wrong secret would sign images that every loader refuses.

  3. Signs with key id 0 (tools/ota_release.py, --security-version defaults to 0).

  4. Publishes esp32c6-netstack-<ver>.ota, esp32c6-ota-<ver>.tar and, when firmware/ota/keys/epoch.bin exists, key-epoch.bin.

Test keys: keys/test.key (id 0) and keys/test_backup.key (id 1) are checked in and public. They sign HITL and development images for loaders built with --//firmware/ota:trust=test or the *_testkey targets. Never ship a test-trust loader.

Dev builds: sign with the test keys, or keep flashing over USB.

Procedure (any key; next shown):

  1. Generate it and write the public half straight into the repo:

    bazel run //firmware/ota:ota_sign -- keygen --name next --pub-out "$PWD/firmware/ota/keys/next.pub"

    (Run it from the repo root: bazel run executes in its own directory, so --pub-out needs an absolute path, which $PWD gives.)

    --pub-out writes the header comment (key id, purpose) and the hex in the same format as the other .pub files. It only fills a missing file or an UNSET placeholder; replacing a real key needs --force, and a file name that doesn’t match --name (say --name next --pub-out …/release.pub) is refused. Without --name, a file name that is a key name (next.pub) selects that key. The private half is never written to a file; keygen only prints it.

  2. Copy the private line’s hex to where its row in the table says: the named repository secret (Settings → Secrets and variables → Actions), or offline storage for backup (and for next until the rotation). Then clear your terminal scrollback.

  3. Check the pair before committing: ota_sign pubkey --key-env <SECRET> (with the private hex in that variable) must equal ota_sign check-pub --in firmware/ota/keys/<name>.pub.

  4. Commit only the .pub file.

On machines without the repo checked out (an offline machine for a backup key), run the ota_sign binary directly with the same arguments, then carry only the .pub file back.

Signer subcommands (bazel run //firmware/ota:ota_sign -- …):

  • keygen [--name N] [--pub-out F.pub] [--force]

  • pubkey

  • check-pub

  • sign --key-id N --security-version S

  • verify --ring 0=release.pub,1=backup.pub

  • epoch --epoch E --revoke IDS --key-id SIGNER

It uses pure-Rust P-256 (RFC 6979 deterministic signatures).

Key rotation¶

The keyring. The loader compiles in a small keyring (gen_key_header.py → ota_key::kRing):

id

name

1

keys/backup.pub

offline, in cold storage; signs key-epoch records (and images, in an emergency)

2

next

keys/next.pub

a planned successor, committed one loader release before CI switches to it

An UNSET entry verifies nothing. A manifest names its key id, and the loader verifies it against that key only. The id has to be in the ring and must not be revoked; otherwise the loader refuses with unknown_key or revoked_key.

Key epochs. A key-epoch record is 80 bytes: magic, an epoch number, a revoked bitmask of key ids, and the signer’s key id, followed by ECDSA r‖s over those 16 bytes. Any trusted, unrevoked ring key can sign one. Clients send the newest record they have in ota_begin.key_epoch. The release asset key-epoch.bin is fetched by update_firmware, and the web app reads it from the bundle.

The loader accepts a record only if:

  • its epoch is above the stored epoch;

  • its revocations include every revocation already stored (they never shrink);

  • it doesn’t revoke its own signer;

  • its signer isn’t already revoked.

It then persists kepoch / krevoked in NVS (namespace splanc_ota). An older or equal epoch is ignored. Neither value is ever lowered, and an NVS erase (USB --erase-fs) is the only reset. ota_status reports key_epoch, revoked_keys and security_floor.

Anti-rollback:

  • The version check is not a security boundary. It refuses a lower manifest version unless allow_downgrade is set, but the client sets that flag, and so could anyone on the LAN replaying an old, validly signed image.

  • The security floor is the boundary. The loader keeps sfloor, the highest security version it has installed, raised at every successful install, and refuses any image below it (security_floor) whatever allow_downgrade says.

  • Releases raise the security version (ota_release.py --security-version N) when they fix a vulnerability. Installing that release makes every older release uninstallable over the air on that device. A USB flash still works: physical access is trusted.

Runbook: planned rotation (release → next)¶

  1. Generate the successor offline: ota_sign keygen --name next --pub-out keys/next.pub. Commit the public half it wrote.

  2. Ship a firmware release. The next migration (USB), or future loader self-update, puts the new keyring on devices. Today the loader changes only over USB, so in practice step 2 rides on the next USB migration. Until then, devices keep trusting only release + backup.

  3. Once every device that matters runs a loader that has next:

    • In the repo, swap the roles: the new key becomes release.pub, the old one moves out.

    • Point the OTA_SIGNING_KEY secret at the new private key.

    • Optionally, sign an epoch (with the old release key or the backup) that revokes the old id, and commit it as keys/epoch.bin.

  4. Destroy the old private key.

Runbook: the release key is compromised¶

  1. Take the backup key out of cold storage. On an offline machine:

    ota_sign epoch --key-file backup.key --key-id 1 --epoch <stored+1> --revoke 0 --out epoch.bin

    Then check it: ota_sign verify-epoch --ring 0=keys/release.pub,1=keys/backup.pub --in epoch.bin.

  2. Commit epoch.bin as firmware/ota/keys/epoch.bin. Every release now ships it as key-epoch.bin, and every client sends it with ota_begin. Each device applies it at its next update attempt, and from then on refuses anything signed by the stolen key. A device that never gets an update attempt stays exposed; push an update to all of them (update_firmware {players: "all"}).

  3. Generate a new release key (keygen --name next --pub-out keys/next.pub --force). Put its private half in OTA_SIGNING_KEY and commit the new keys/next.pub.

  4. Bridge releases:

    • Until loaders carry the new key, sign releases with the backup key (ota_sign sign --key-id 1, by hand on the offline machine), so revoked devices can still be updated.

    • The next USB migration ships a loader with the new key, after which CI signs with it (a planned rotation).

  5. Put the backup key back in cold storage.

The backup key (provisioned 2026-10-22): the owner generated it on an offline machine and committed only the public half, firmware/ota/keys/backup.pub. Every loader built from then on trusts it. Loaders flashed before that have an UNSET backup slot, so a compromise of release can only reach them by a USB re-flash.

To make a replacement backup key, run ota_sign keygen --name backup --pub-out keys/backup.pub --force on the offline machine, or use plain openssl:

openssl ecparam -name prime256v1 -genkey -noout -out backup.pem
openssl ec -in backup.pem -outform DER | head -c 39 | tail -c 32 | od -An -v -tx1 | tr -d ' \n'  # private (64 hex)
openssl ec -in backup.pem -pubout -outform DER | tail -c 65 | od -An -v -tx1 | tr -d ' \n'      # public (130 hex)

Store the private half offline, never in the repo or CI. Commit only the public half.

Loader self-update: not implemented (USB only)¶

Keyring changes, and any loader change, need a USB flash today. Here is why updating the loader over the air isn’t safe in this layout:

  • Only the app can write it. The loader can’t overwrite the factory slot while running from it, so the app would erase and rewrite the 1.5 MB factory partition (≈10–15 s of erase + program).

  • A power cut in that window leaves no valid loader. The app still boots (otadata selects it), but any later crash or rollback lands on an invalid factory image and the device needs USB. There is no second loader copy to fall back to: flash is full, with 95 KB spare in the loader slot.

  • A bad loader has the same effect, even when correctly signed.

  • What a safe version would take: an A/B loader pair. That doesn’t fit in 4 MB next to a 2.2 MB app slot. An alternative is a tiny immutable first stage that picks between two loader images, which would also have to fit. FLAG_LOADER stays reserved and refused until then, so a loader image can’t be installed by accident.

Flow:

  1. ota_begin to the app gets REBOOTING.

  2. The client reconnects to the loader (its welcome has ota.mode = MODE_LOADER and features ota, loader, tls_info).

  3. ota_begin again gets RECEIVING plus offset.

  4. Each ota_chunk gets ota_status with the next offset (stop-and-wait, one TLS record per chunk).

  5. ota_finish gets INSTALLED; the device boots the app.

  6. get_ota_status reports last_result (ok or rolled_back).

Resume: progress is persisted every 64 KB and at the end. ota_begin with the same manifest resumes at the persisted offset rounded down to a sector. That sector is erased again, so a half-programmed sector never survives into the image (session.rs; every cut point is exercised on a simulated NOR flash in ota_test).

Throughput: 4 KB chunks. Each chunk costs one RTT plus a ≈40 ms sector erase and a 4 KB program. See the HITL numbers for the rig’s tunnelled path.

Other requests: the loader also answers hello, time_sync_ping and get_tls_info, so a stock client’s connect sequence completes. Every other arm gets error{unsupported}. The loader decodes ClientMessage by hand (firmware/ota/src/wire.rs), and wire_test checks every field number against the generated host bindings.

Pull from GitHub: the loader doesn’t fetch images itself. The netstack has no TLS client, so a pull through https://splanc.pages.dev/gh-asset would need one. Clients push instead, which works from a phone, a laptop, the agent and the bridge.

UX¶

  • Web app, Flash screen: when the connected device advertises ota (or sits in its updater), the screen offers “Update ⟨name⟩ over Wi-Fi” above the USB flash. It needs no Web Serial, so it also works on iOS and Android. Progress shows handoff, transfer %, verify, reboot and the health check.

  • Device in the updater: the connection pill reads “in updater” and a toast points to the Flash screen.

  • Package source: the .ota comes from the release bundle esp32c6-ota-<ver>.tar, which carries it inside, or from a cached copy for offline use.

  • Entry point: the connected device’s own sheet (Devices) has Update firmware; the add-device row’s chip icon is for flashing a new board over USB. Before offering the Wi-Fi button the sheet asks the app for get_ota_status: a legacy-layout app (it still advertises ota) gets the “needs a one-time USB update” note instead.

  • Driver: web/src/net/otaUpdate.ts, shared with the agent.

  • Reconnects (the browser path): the app and the loader restart without closing the socket, so the browser’s socket goes half-open and only TCP keepalive (Chromium: 45 s) would notice. After a REBOOTING/INSTALLED reply the driver waits 1.5 s and calls expectRestart(), which abandons the socket at once (a browser close() waits ~60 s for a closing handshake the restarted peer never answers). While any waitForWelcome is pending the client keeps retrying the same target at a ≤2 s backoff, past its cert-trust give-up, until the wait’s own deadline (180 s per restart). The sheet shows “Waiting for the updater (N s)”; a timeout ends in a failure with recovery text, never a silent spinner. A device that comes back as the app is asked again (up to 3 handoffs). Chunk and begin replies get 30 s (as in the Python client); a timed-out chunk resumes on a fresh connection.

  • Agent: update_firmware {version: "latest" | X.Y.Z, allow_downgrade?, players} fetches the release’s .ota (esp32c6-netstack-<ver>.ota). For development, set SPLANC_OTA_PACKAGE=path. It rolls out canary-first: one player alone, and the rest in parallel only if it came back healthy. This is the swarm’s canary rule turned into a rollout policy. It reports MCP progress (notifications/progress) per phase and per 10 %.

  • Bridge: it hosts the same MCP server, so update_firmware {players: "all"} updates every fixture.

One-time migration (USB, from the legacy layout)¶

The new app slot covers the old littlefs region (0x310000–0x3F0000), so a single write of all five images would destroy the user’s maps and TLS identity before anything could copy them. The migration runs in two phases:

  1. Write everything below the app slot: bootloader, table, erased otadata, loader. Nothing at or after 0x1C0000 is touched, so the old filesystem is intact.

  2. Reset. The loader boots first (otadata is erased) and, on its first boot:

    • formats the new littlefs at 0x160000;

    • mounts the old region read-only through a hand-made partition view (it overlaps app, so it can’t be registered);

    • copies every file across (temp files skipped);

    • writes /lfs/.ota_migrated;

    • logs [loader] migrate: done legacy=1 copied=N failed=0.

    Until the marker exists, every boot redoes the copy from a fresh format, so a power cut mid-copy just starts over.

  3. Write the app (phase 2). The loader finds a valid app and boots it. NVS (Wi-Fi credentials from #311) was never touched.

Who runs it:

  • The web flasher reads the board’s partition table first. A table without a factory loader means the legacy layout, and it runs the two phases. Between them it waits wait_seconds, reconnects to the ROM, and refuses to write the app unless the new littlefs superblock exists. If the loader never ran, the user’s data is still in the old location.

  • A board that already has the OTA layout takes a plain single-phase write.

  • The bundle’s flash.json carries an ota block (app_offset, legacy_migration.phase1_below, wait_seconds, package).

  • Release assets:

    • esp32c6-ota-<ver>.tar is the new layout. Older web apps don’t match that name, so they can’t single-phase it by accident.

    • esp32c6-netstack-<ver>.tar is still published in the legacy layout. That app runs and answers get_ota_status with error=legacy_layout.

Testing¶

Host tests (all in bazel test //...):

  • //firmware/ota:ota_test covers:

    • SHA-256 known answers;

    • the manifest layout;

    • the image-header gate;

    • offer checks;

    • ordering and erase planning;

    • persist cadence;

    • every power-cut point resuming to the exact image on a simulated NOR flash;

    • the loader decision table;

    • the crash-loop counter;

    • the health verdicts.

  • :wire_test checks the hand codec against the generated bindings.

  • :sign_test uses real P-256: sign, verify, tampering, wrong key, and KAT drift.

  • //firmware/loader:layout_test holds the size and layout invariants above.

  • //web:otaUpdate_test and //pi/hitl/tests:hitl_test (test_ota_core.py) run the web and Python drivers against a simulated device: handoff, reset mid-stream and resume, rollback, bad signature, legacy layout.

  • //web:partitionTable_test and //agent:firmware_test cover table parsing, package resolution and the canary rollout.

Web journey (//pi/hitl/harness:web_ota_journey, tags hitl_web + manual, opt-in): the same update through the real web app in headless Chromium, through lan_relay.py in the reservation container (a phone’s LAN socket semantics; it can emulate a slow Wi-Fi rejoin after each restart and a mid-transfer stall). The OTA gate below drives the Python client, which can’t see a bug in the browser path.

HITL gate (//pi/hitl/harness:ota_gate, tags hitl + manual, one reservation):

  1. migrate: legacy bundle, provision, upload a 120-LED map, read the cert pin, then the two-phase USB migration. The device must rejoin with no provisioning, with the same cert and the same stored map bytes.

  2. upgrade: A → B, which reports +b.

  3. crash: an image that aborts at boot rolls back; B over the air recovers it.

  4. unhealthy: an image with no render task fails health at 120 s and rolls back; B recovers it.

  5. powercut: a chip reset half way through the transfer, then resume and verify. The rig can reset a DUT over USB but can’t cut its power. The reset aborts the flash write the same way, and its reset reason is external, like a power-on.

  6. badsig: one flipped signature bit is refused (bad_signature), and the device returns to its app.

Every image is signed with the test key, for the test-key loader.

The core (firmware/ota: manifest, session, boot decisions, health) is no_std, dependency-free Rust, so a future swarm-plus-splanc loader can share it, as the swarm’s swarm/net is shared today. Its transports sit on top of the same manifest and boot decisions.

Limitations and follow-ups¶

  • Loader updates are USB-only. They need their own anti-brick story (a bad loader has no recovery).

  • Post-validation hangs become a counted reset only if a watchdog fires; the task WDT watches the idle task, not the loop task.

  • No true power-cut on the rig: the reset test stands in for it.

  • littlefs is 192 KB (was 896 KB). That is enough for today’s data, but an on-device effect library would need flash that a 4 MB part doesn’t have.

  • The OTA client is single-session per device. An update holds the device’s wss slot for its duration.

Rejoin after a reset (netstack). After an unplanned reset in the middle of traffic, the AP can keep a stale association for the factory MAC and ignore authentication. Run 8 papered over this with a 12 s random-MAC fallback in this branch; that duplicated #336’s join guard (a sequence-numbered disassoc + deauth goodbye re-sent every second, random MAC only after 60 s) and has been removed. OTA adds one thing on top: before a planned restart (handoff, install, ota_reboot) netstack_prepare_restart() sends the same goodbye straight away, so the next boot’s join doesn’t have to wait on the guard.
