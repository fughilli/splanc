Wi-Fi rejoin policy and render isolation (netstack C6)¶

Status: implemented (netstack build). Follows #363, which removed the reboot-to-rescan: the board now finds a missing network with an in-place background sweep while the effect keeps playing.

Two questions drove this:

  1. Do scanning, joining or failing to join disturb the LED output on the single-core C6?

  2. How should the board (re)join when it isn’t on its network, including a unit that is set up on an AP once and then deployed somewhere it will never see that AP again?

1. Render isolation¶

Loop priority¶

The netstack loop runs one priority below render whenever the link is joining, scanning, leasing, deriving a PMK, or idle, so none of that work can delay a frame. It moves up to render’s priority only while a wss session is open on a leased link with no sweep or PMK derivation running (netstack_data_plane_active, re-checked every loop). Equal priorities are time-sliced per 1 ms tick whenever both are runnable, so a streaming session gets about half of a busy CPU. A rejoin always tears the session down first, so the rejoin path never runs at render’s priority.

Keeping the loop below render all the time starved streaming. It then ran only in render’s sleeps: about 3-4 ms of each 12 ms frame under a light 80 fps effect. The harness arms the analyzer after the console attach, grades nothing in the first 2 s of a capture, and issues each phase’s command 2.5 s in. A field unit has no console host attached.

The gate (wifi_cadence, --gate) fails on any wire frame interval in a scan / join phase that deviates from the steady median by more than max(3 ms, 2 % of the period, 1.5 × the steady phase’s p99.9 deviation), on a damaged frame, or (without an analyzer) on a render / wire-out interval beyond the steady maximum by 4 ms. Infra problems are SKIP.

2. Rejoin policy¶

Persisted in NVS (wifi_pol), applied without a reboot, and settable from the app’s device settings, the agent (set_wifi_policy / get_wifi_policy), the BLE player transport (the same protocol arms), and the wired console:

WIFI MODE <auto|fixed|manual|offline> [cap=S] [every=S] [decay=H] [sparse=S] [force]
WIFI REJOIN        WIFI STATUS
WIFI SCAN | DHCP | GIVEUP   (link diagnostics)

Mode

Behaviour when the network is missing

auto (default)

Background sweeps 5 s, 10, 20, 40 … up to scan_cap_s (default 60), then every scan_cap_s for as long as the network is missing. Opt-in decay: after decay_after_h hours (default 0 = off) without ever seeing the network, at most one sweep per sparse_interval_s (default 900).

fixed

One sweep every interval_s (default 300).

manual

Never scans or joins on its own. A rejoin command or a new provision opens a 2 min join window (the auto backoff inside it). A dropped link stays down until told.

offline

The radio is off: never started at boot, no scans, no RF. Switching to offline at runtime goes silent at once (goodbye to the AP, no TX, MAC released to sleep); the radio is fully off from the next boot. The show plays; BLE and the console stay up. Credentials are kept.

Decay is opt-in¶

Auto mode keeps its backoff cap indefinitely unless the user enables the decay (decay_after_h > 0, e.g. 24 h → 15 min). The decay saves airtime and power when a network is gone for good (each sweep is ~1.6 s of channel hopping), but it also makes a returning network take up to sparse_interval_s to be noticed, and a board whose AP was only off for a long weekend should rejoin within a minute. #371 shipped it on by default (24 h); it became opt-in afterwards, by user decision. Decaying to offline instead would strand units, so offline is only ever an explicit choice. When enabled, the unseen time is persisted hourly (wifi_unseen), so a nightly power cycle doesn’t reset the clock.

Migration. The NVS record is written whole on any change, so a v1 record (firmware with the 24 h default) carries decay_after_h = 24 whether or not the user ever chose it. Version 2 of the record has the same layout; on load:

Stored record

decay_after_h after the upgrade

none (never changed the policy)

0 (the new default)

v1, decay 24

0: read as the old default, never chosen

v1, any other value (0, 12, 48 …)

kept: an explicit choice

v2 (written by this firmware)

as stored, 24 included

A user who had explicitly typed 24 h on old firmware loses it and has to set it again; that case can’t be told apart from the default. Downgrading to old firmware rejects a v2 record and falls back to the old defaults (decay on).

Forward-deployed units¶

The intended flow: set the unit up on an AP (map, effects, settings, maybe an OTA update), confirm any update, then switch it to offline from the app, the agent or the console while it is still connected. Credentials stay stored, so auto later rejoins without re-entering them. In the field it is reconfigurable over BLE (the player transport, or Improv) and the wired console. A new provision while offline switches the mode back to auto and brings the radio up in place.

There is no SoftAP and no physical button on the netstack build. BLE and the console are the escape hatches.

OTA interaction¶

A freshly installed update boots pending verification and must prove itself before a deadline, or it rolls back to the loader. The rules:

  • Going offline / manual while an update is unconfirmed is refused (refused: "ota_pending") unless forced. The app warns and asks twice before forcing; the agent never forces unless explicitly asked.

  • The health check requires a lease only when one is expected: the policy lets the board join on its own (not offline, not manual outside a window) and the network was seen this boot. An AP that is simply absent (a unit moved to the field right after an update) is no evidence against the image, so it is confirmed on rendering alone and never rolls back merely because the AP is gone. An AP that is present but can’t be joined still rolls a broken image back.

  • In offline mode the TLS-ready requirement is waived too (there is no TLS server).

  • The OTA loader (recovery) ignores the policy and always tries to get online.

Status¶

get_wifi_policy reports the mode and fields, the link state (offline / unprovisioned / idle / searching / joining / joined), seconds to the next sweep, sweeps run, the SSID, how long the network has been unseen, whether the decay is in force, ota_pending, and radio_on. The app’s device sheet shows it as one line (“Wi-Fi: offline mode”, “Wi-Fi: rejoining, next scan in 40 s”, …).

Scope notes¶

  • fixed has no time-of-day schedule windows (the board has no reliable wall clock).

  • The vendor-WiFi (lwIP) build advertises the feature through the shared player core but does not act on it. That build is deprecated.
