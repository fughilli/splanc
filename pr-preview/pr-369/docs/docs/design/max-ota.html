Splanc MAX updates over the air¶

Status: implemented (PR “Splanc MAX over-the-air updates”). HITL results at the end.

A Splanc MAX is a Raspberry Pi driving a Tang Nano 9K FPGA (the spi_ws281x gateware) over SPI. Until now it could only be updated by re-flashing a pi-v* SD image or by a developer running deploy_live with the deploy key. Now a MAX updates the way a C6 fixture does: the web app’s “Update over Wi-Fi”, the agent’s update_firmware and the bridge all work, with one dispatch on the device.

What is different from the C6 (docs/design/ota.md):

  • The unit is a whole NixOS system, not a 2 MB app image.

  • The Pi downloads its image itself. The client sends only the 108-byte signed manifest.

  • A new system is booted exactly once. It is kept only after the player proves healthy. Otherwise U-Boot’s default, the old system, comes back by itself: after a crash, a hang, a reset or a power cut.

Why the generation.

  • SD wear. nix-store --import skips every path already in the store, so an update writes only what changed. A delta image (below) doesn’t even transfer the rest. An A/B root rewrites the whole filesystem every time.

  • Power-loss safety. Each store path is written, then registered in the Nix database in one SQLite transaction; a cut leaves an invalid path that the next import rewrites. Every file the updater writes outside the store is temp + fsync + rename + fsync(dir). Most importantly, the default boot entry (/boot/extlinux/extlinux.conf) is not touched until the new system has proven healthy (see Trial boot), so the state after a cut is always “the old system”, or “the new system, healthy and committed”.

  • State survives for free. A generation switch leaves /etc’s stateful parts and all of /var alone. An A/B root would have to move Wi-Fi, identity and the stored map onto a third partition, then re-partition every card in the field.

  • It’s what NixOS already does. deploy_live is nix copy + nix-env --set + switch-to-configuration. OTA adds the download, the signature, and when the switch happens.

Trial boot (one-shot)¶

The released fleet is Pi 3. The Pi 3, Pi 4 and Zero 2W boot through U-Boot + extlinux (nixos-raspberrypi’s default). The Pi 5 boots its kernel straight from the firmware (see “Boards”).

The Pi 3 firmware has no tryboot, so the one-shot lives in U-Boot. pi/provisioning/nix/ota.nix builds U-Boot 2025.01 (rpi_arm64_defconfig) with a PREBOOT that runs before the stock bootflow scan:

pci enum; usb start;
if load mmc 0:1 ${scriptaddr} splanc-trial && itest.b *${scriptaddr} == 0x31; then
  mw.b ${scriptaddr} 0x30 1; fatwrite mmc 0:1 ${scriptaddr} splanc-trial ${filesize};
  sysboot mmc 0:2 any ${pxefile_addr_r} /boot/extlinux/splanc-trial.conf;
fi

  • /boot/firmware/splanc-trial (FAT) holds 1 <nonce> when armed.

  • U-Boot rewrites the first byte to 0 before it loads the trial kernel, so the trial boots once.

  • Anything that fails returns to the stock boot, which reads extlinux.conf, which still names the old system. That covers no flag, a 0, a missing trial conf and a missing kernel.

  • The trial entry /boot/extlinux/splanc-trial.conf is written in the NixOS extlinux builder’s own format, with the builder’s file names (pi/max_ota/src/extlinux.rs). Its APPEND adds splanc.ota=trial.

  • Any later switch-to-configuration deletes boot files no generation uses. A stale trial can therefore only vanish; it can never become a default.

Flow¶

client: ota_begin{manifest, source_url?}         player (unprivileged): check signature,
        <- ota_status{DOWNLOADING}               board, key, version; write inbox/request
root updater (splanc-ota-apply, path unit on the inbox):
   check again (the authority) -> curl -C - into dl/<sha>.part  (resumable)
   size + SHA-256 = the signed digest -> dl/<sha>.img
   header: board + version must match the manifest; delta base paths must be valid
   zstd -dc | nix-store --import -> GC root on the new toplevel
   copy kernel/initrd to /boot/nixos, write splanc-trial.conf, state = staged,
   THEN arm the flag (1 <nonce>)                 <- ota_status{INSTALLED}
   reboot
U-Boot: flag 1 -> 0, sysboot the trial
splanc-ota-boot (every boot, before the player): booted == new && splanc.ota=trial -> trial
splanc-ota-health: player healthy before the deadline?
   yes -> nix-env --set + switch-to-configuration boot (extlinux default = new),
          drop the trial entry, raise the security floor, collect garbage -> "ok"
   no  -> state "rolled_back", reboot -> U-Boot boots extlinux.conf (old)
client: polls get_ota_status through the reboots until last_result ok / rolled_back

Power loss at every step¶

//pi/max_ota:updater_test cuts the power at every mutating step of a whole update, from the request to the commit (30 cut points). The fake Pi has a filesystem, a Nix store, a web server, U-Boot’s PREBOOT and the extlinux builder.

Every cut point recovers:

  • the Pi boots a complete system, old or new, never anything else;

  • if it boots the new one, that system is committed (ok) and is the extlinux default;

  • if it boots the old one, extlinux.conf still names it;

  • a retry from the client then always reaches the new system.

Outcomes over the 30 cut points: 25 end on the new system with no retry, because a cut during the download resumes and a cut during staging re-stages. 3 roll back. 2 lose the request before it was persisted.

Signing¶

The manifest is the C6’s 108-byte manifest, unchanged (splanc_ota::manifest): version, size, SHA-256 of the image, flags, then ECDSA P-256 r‖s over SHA-256 of the first 44 bytes.

The keyring: the C6’s own. A MAX trusts exactly the keys the C6 loaders trust, from the same source: firmware/ota/ring.bzl holds RELEASE_RING / TEST_RING, which //firmware/ota (the loader’s C++ header) and //pi/max_ota (a Rust const, gen_key_header.py --lang rust) both generate; MAX_RELEASE_RING / MAX_TEST_RING are the same dicts, not copies. --//firmware/ota:trust=test swaps in the TEST keys (test, test_backup) for both.

An UNSET entry verifies nothing. A manifest names its key id and is verified against that key only. There are no MAX-specific key files and no MAX-specific secret.

The board is the separation. With shared keys, a C6 image is validly signed as far as a MAX is concerned, and vice versa. What keeps them apart is the signed board field, checked on both sides:

  • A MAX refuses board 0 (a C6 image) and any board but its own, as wrong_board, before anything is downloaded (verify::check_offer).

  • A C6 refuses any board but 0, as wrong_board: the app’s pre-check and the loader both go through splanc_ota::session::check_offer.

  • Never a bare sha256 (contrast pi/bridge/selfupdate.py).

  • Who checks. The player checks every offer for a quick answer. The root updater checks it again before it downloads anything; it is the authority.

When separate keys would be worth revisiting. Sharing is right while the C6 and the MAX ship from the same repo, the same release and the same CI secret holders. If the MAX ever gets its own distribution channel (a separate release stream or mirror), or different people should be able to sign MAX systems than C6 firmware, give the MAX its own key: ids 3 (max, online) and 4 (max_backup, offline) are reserved for that, in no ring today. Moving to them is a normal rotation (below): ship a system whose ring has 3/4, then revoke 0/1 for the MAX.

Key epochs. The same record as the C6: the updater applies the release’s key-epoch.bin (from firmware/ota/keys/epoch.bin), sent in ota_begin.key_epoch by the web app and the agent. The rules are the C6’s (docs/design/ota.md “Key rotation”): the signer must be a provisioned ring key (unknown_key otherwise), the epoch must rise, revocations never shrink, a record can’t revoke its own signer, and a revoked key signs nothing more, records included. The revocations are device state (/var/lib/splanc-ota), so they outlive every later update; only a re-flash resets them.

Key rotation¶

It is the C6’s (docs/design/ota.md “Runbook: the release key is compromised”), and one key-epoch.bin covers both kinds of fixture. What differs on a MAX:

  • The ring ships over the air. It is part of the system image, so a MAX bridge release can carry a new ring (the C6 needs a USB migration for that).

  • Bridge images are signed by hand with the backup, on the offline machine, until units trust the successor key:

    python3 tools/max_ota_release.py --toplevel <system> --board pi3 --version X.Y.Z \
  --signer ota_sign --pubkey firmware/ota/keys/backup.pub \
  --key-id 1 --key-file backup.key --out-dir _assets

    CI never does this: there is no backup secret, and max_ota_release.py refuses --key-id 1 without --key-file.

  • Revoked ids are never reused, on either kind of fixture: a successor key takes next (2) or another free id.

The tests (//pi/max_ota:updater_test) run this end to end with the TEST keys: a backup-signed (id 1) record revoking release (id 0), after which release-signed images are refused and backup-signed ones install.

Anti-rollback. It works exactly as on the C6:

  • allow_downgrade lets a client install an older version;

  • the security floor (raised at every commit) refuses older security versions regardless.

Download¶

  • The client sends only the manifest. The Pi fetches the image itself. It is not streamed over the control connection: a phone can sleep, a laptop can close, and the agent can be on another network. The Pi has a full TLS stack (curl) and its own network, so the update carries on regardless.

  • Where it fetches from. By default, the release asset for the manifest’s version and the Pi’s board: https://github.com/fughilli/splanc/releases/download/firmware-vX.Y.Z/max-<board>-X.Y.Z.nixclosure.

  • ota_begin.source_url (new field 4) overrides it with any http(s) URL: a LAN mirror for a MAX without internet, a development build, or the HITL gate’s tunnel. The URL decides nothing about what installs; the signed digest does.

  • Resumable. The download is curl -C - into dl/<sha>.part, flushed every second, so a power cut keeps what arrived. At boot, splanc-ota-apply resumes it. It retries 5 times with backoff, then download_failed: <curl error>.

  • Verified before use. Nothing is imported until the whole file’s size and SHA-256 match the signed manifest.

The image (.nixclosure)¶

SPLANC-MAX-OTA 1
board: pi3
version: 1010000
toplevel: /nix/store/…-nixos-system-ledmapper-…
compression: zstd
base: /nix/store/…        (delta only: paths left out, which the device must have)

<zstd(nix-store --export <paths>)>

The manifest’s size and SHA-256 cover the whole file, header included.

  • Full image: the whole closure.

  • Delta (--base-toplevel): only the paths the base system doesn’t have. The updater checks every base: path is valid before importing anything (missing_base otherwise).

tools/max_ota_release.py packs and signs both (stdlib Python, nix-store, zstd, ota_sign).

Health proof¶

The player (pi/player_rs) writes /run/ledmapper/health every 2 s:

  • listening=1 once its WSS listener is bound;

  • ticks: the frames its render loop pushed to SPI;

  • up_ms.

The trial is kept only if, before the 300 s deadline, all of these hold (splanc_max_ota::health, host-tested):

  • the player has been up for ≥ 20 s;

  • it is listening;

  • ticks advanced across two samples ≥ 5 s apart;

  • if the old system had a default route when it staged the update, the new one has one too.

Why the network rule. A system that can’t reach the network can’t be fixed over the network, so it isn’t kept. Unlike the C6, a MAX that loses its AP for the trial’s duration just keeps the old system, and the update can be retried.

The deadline. It counts from the trial’s boot reconcile and uses CLOCK_BOOTTIME (a Pi has no RTC, and NTP moves the wall clock after boot). It is long because the player starts only after the FPGA is re-flashed with the new gateware, when the gateware changed.

FPGA bitstream versioning¶

The gateware is part of the system. It is the Bazel-built spi_ws281x_tangnano9k.fs, in the closure as build_data. The Tang is commissioned at every player start (fpga.nix / apps.nix):

  • The sha256 of the .fs is stamped into the Tang’s own SPI flash at 0x300000.

  • The bitstream is re-flashed only when the stamp differs.

A trial boot of a new gateware flashes it, and a rollback flashes the old one back: the gateware always follows the system that booted, with no Pi-side state to drift.

Power-loss fix (this PR). The commission now invalidates the stamp before flashing. Before, a cut mid-flash left the previous gateware’s stamp next to a half-written bitstream, so the next boot of that previous system skipped the flash. That is exactly the rollback case.

Transport (ledmapper.proto)¶

Messages. The same arms as the C6: ota_begin / get_ota_status / ota_abort → ota_status. The additions:

  • OtaBegin.source_url = 4

  • OtaStatus.board = 17

  • OtaStatus.State.STATE_DOWNLOADING = 6

  • the welcome feature ota_pull

How the player answers. pi/player_rs/src/ota.rs uses the loader’s zero-copy codec (splanc_ota::wire, now with those fields). The host profile’s by-value envelopes overflow a worker stack.

  • ota_begin: DOWNLOADING, or FAILED + error.

  • get_ota_status: mode APP (a MAX has no loader), the state mapped from the updater’s phase, offset = bytes downloaded, board, app_version, last_result, key state, max_chunk = 0.

  • ota_chunk / ota_finish: pull_only.

What the player and the updater share. The player is unprivileged (user ledmapper) and talks to the root updater only through /var/lib/splanc-ota/inbox/ (group-writable) and the world-readable state file.

Error codes added for MAX: wrong_board, busy, bad_url, pull_only, download_failed, bad_image, missing_base, import_failed, bootloader_unsupported.

UX and clients¶

  • Web app. web/src/net/otaUpdate.ts updateFirmware dispatches on ota_pull: pullUpdate sends the manifest and follows the device through download → verify → reboot → health, reconnecting across reboots. The Flash screen shows “Update ⟨name⟩ over Wi-Fi” for a MAX. It fetches max-<board>-<ver>.manifest (and the shared key-epoch.bin) from the selected release, with board taken from ota_status. Progress reads “The device is downloading the firmware… n%”, then the C6’s verify / reboot / health steps.

  • Agent update_firmware. It resolves one package per kind of player: the C6 .ota, or the board’s manifest. A mixed fleet still rolls out canary-first. For development, SPLANC_MAX_OTA_MANIFEST and SPLANC_MAX_OTA_SOURCE_URL override the release.

  • Bridge. It hosts the same MCP server, so it is unchanged.

  • Python (HITL). ota_core.pull().

Release artifacts and cadence¶

MAX images are built alongside the firmware releases: the max job runs on every firmware-v* tag, after the C6 job, onto the same release.

  • The version. The system is stamped with the release version (SPLANC_MAX_VERSION → /etc/splanc-max/version), so “latest” names the same version for every fixture.

  • The key. The job fails, like the C6 job, if OTA_SIGNING_KEY is missing or isn’t release.pub’s private half.

  • SD images. pi-v* SD images keep their own tag. They report version 0 (0.0.0-dev) until their first OTA, so any release updates them.

Migration (once)¶

pi-v1.0.0 units have no OTA arms, no updater and a stock U-Boot. They need one of:

  • a new SD image (the next pi-v*);

  • bazel run //pi/provisioning:update -- <host> / deploy_live.

That first OTA-capable system installs the trial U-Boot on the firmware partition (the U-Boot builder copies it at every switch) and seeds the persistent deploy key. From then on, everything is over the air. Until then the updater refuses with bootloader_unsupported, so the C6 clients’ “Update over Wi-Fi” can’t strand a v1.0.0 unit.

HITL gate (//pi/hitl/harness:max_ota_gate, a py_binary tagged hitl + manual). Its images are Nix-built: pi/hitl/max_ota_images.sh OUT builds A/B/U with TEST trust and packs deltas. It runs on rig-1’s pi-ledmapper-1/2 in one reservation:

  • setup: deploy A over SSH and record the state;

  • upgrade: A → B;

  • badsig;

  • unhealthy: U rolls back to B;

  • powercut: B → A with an immediate reset mid-download, then resume;

  • trialcut: A → B with a reset during the trial; back on A.

The network DUTs have no switchable power. echo b > /proc/sysrq-trigger resets immediately, with no sync and no unmount, which is what a cut does to the filesystem. Journals of the OTA units and the player are saved per phase.

What the owner must do (decisions)¶

  1. Nothing for signing keys. A MAX uses the C6’s keys: the existing OTA_SIGNING_KEY secret / release.pub and the offline backup.pub. There is no MAX key to create, no MAX secret and no MAX key file. The C6 runbooks (docs/design/ota.md “Key rotation”) now cover MAX units too.

  2. Revisit separate keys only if the MAX gets its own distribution channel or its own signers (see “Signing”); ids 3/4 are reserved for that.

  3. Internet for MAX units. By default the Pi downloads from github.com. A fixture on an isolated LAN needs a mirror passed as source_url; the bridge could serve one. That is not built yet.

Limitations and follow-ups¶

  • Pi 5 / Pi 4 / Zero 2W aren’t wired yet (see “Boards”). Pi 5 needs its tryboot backend.

  • Release images are full closures. Deltas exist in the tool and the updater, but CI doesn’t keep the previous release’s closure to diff against.

  • A trial that changes the gateware re-flashes the Tang twice on rollback (new, then old). That is a few seconds of dark LEDs each time.

  • The first OTA-capable system needs a deploy or an SD flash (Migration).

  • The updater keeps the current and the previous generation. A full disk shows up as import_failed or flash_error.

What the first runs found, all fixed in this PR:

  • The player SEGV’d at start. On main the host-profile Player::handle needs 8.2 MiB of stack (sub sp, #0x82b000), more than the 8 MiB main thread and the 8 MiB tokio workers. Both --start N and every client frame crashed the static-musl player in a loop. It now runs on 32 MiB stacks.

  • spidev’s 4 KiB buffer. It made every 6.6 KB FPGA frame (4 × 550 LEDs) fail with EMSGSIZE, silently, so the Tang got nothing. The image now sets spidev.bufsiz=65536, and the player logs the first write error. The health check, which counts frames that reached SPI, caught this.

  • The baked hostname. It made avahi advertise ledmapper.local, which would have broken the rig’s splanc-max-2.local addressing. Now the hostname comes from /var/lib/sbc (see “Device state”).

  • The health service lost its first sample across ticks; now the caller carries it.

U-Boot under QEMU. Before deploying the trial U-Boot to hardware, it was run under QEMU raspi3b against a two-partition SD image. The flag 1 abcd became 0 abcd; 0 … and an absent flag were left alone.
